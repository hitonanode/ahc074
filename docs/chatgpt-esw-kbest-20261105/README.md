# 区間DPの候補多様化と、補助紙を戻し切らない注文処理

## 結論と比較対象

**固定設計・fallbackなしの新規128ケースで、広探索版は添付元実装比で総手数を0.366935%、前回の統合版比で0.243901%削減した。** ケースごとの `100 log(候補/基準)` の平均では、それぞれ **−0.367662 ± 0.018255% SE**、**−0.244263 ± 0.012715% SE**。勝／分／敗は元実装に125／0／3、前回統合版に123／0／5だった。

ただし、広探索版は計算量が大きい。**同じ2秒予算での改善ではない。** 少数ケースの設計読込後のCPU時間は、基準の中央値0.970秒に対して約2.780秒だった。これは設計探索を含まないので、この版をそのまま提出推奨とはしない。

移植の第一候補は、**局所の区間DPから異なる紙の組合せを3候補ずつ残す変更だけ**である。紙設計も長期価値モデルも変えず、128件で **−0.138200 ± 0.012367% SE、103／1／24**、総手数1,843手を削減した。中央値CPU時間は約1.145秒で、広探索版より小さな変更・追加費用である。

比較基準は `eject-single-window.cpp`、Git blob `8136e2455cc70038e3f7993ac1e7979d3ed2767f`、SHA-256 `5f58f1c24f8a643c589124bad0b93d29c35d029a2c7d6ca9f2964726ff7b4bdd`。リポジトリの `solutions/eject-single-window/main.cpp` と一致する。**最新mainの esw-climb4 に対して測った数値ではない。** 最終確認したmainは `21151b53e5ff0a34e0cd59323a36457a5a4dd5c4` で、[PR119](https://github.com/hitonanode/ahc074/pull/119) の変更が入っている。

研究結果を共有するNOT FOR MERGEのDraft PRであり、既存解法や共通評価履歴は変更しない。0.5%改善、上位参加者を上回ったこと、2秒への適合は主張しない。

## 読む場所と生成するC++

`build.py` は、このディレクトリの固定した `baseline.cpp` に差分を厳密適用し、単独でコンパイルできるC++23ファイルを作る。基準・差分・生成結果のSHA-256をすべて検査し、文脈の曖昧な一致やfuzzは許可しない。

| profile | 内容 |
|---|---|
| `lean` | 新しい区間DP候補3系統×2文脈だけ。列MDP、warm helpers、各候補へのejectionは加えない。 |
| `wide` | 列MDP0.25＋区間DP7系統×2文脈＋warm helpers＋後処理4系統＋候補別ejection。品質調査用。 |
| `research` | 比較とアブレーション用。既定は元の注文処理で、環境変数で各実験を有効化する。 |


主変更を読むには、まずテキストの `kbest.patch` が短い。主要オンライン実験を含む差分は `research.patch.gz`。不採用の二枚capソースは会話に添付したソースZIPの `two-caps` profileに保存した。圧縮は保存量を抑えるためだけで、生成するソースの内容はmanifestで固定されている。GitHubでは圧縮差分を `patch-parts/` に分割保存し、build.pyが結合する。ソースZIPでは結合済みの.gzも収録する。展開にはPython標準ライブラリだけを使う。

```sh

python3 build.py wide generated/wide.cpp
python3 build.py research generated/research.cpp

g++ -std=c++23 -O2 -march=native -DLOCAL_BENCH generated/lean.cpp -o generated/lean
g++ -std=c++23 -O2 -march=native -DLOCAL_BENCH generated/research.cpp -o generated/research
g++ -std=c++23 -O2 checker.cpp -o generated/checker
```

## 1. 見つかった探索上の盲点

元実装は、前の商品紙の返却や古い補助紙の扱い方を複数試し、操作する紙の列が異なる上位2系統を後処理する。ここは既に強い。

しかし、その各計画の内部で使う **穴埋めの区間DPは最良解を一つしか返さない**。後処理へ渡る前に、別の紙を使う同点解・僅差解が消えていた。

区間DPの概算は、主に「今の列頭を基準に何回の掘りを省くか − 補助紙の取得・設置費用」。一方、完成した計画の評価は、実際の合法な操作数、列外紙の将来の返却費用、再利用可能性、列の残り方、後処理による削除・差込先変更まで含む。

したがって、区間DPで同点の二つの配置でも、最終的な価値は同じとは限らない。上位の計画数を2から4へ増やすだけでは、内部DPで捨てた配置は復活しない。今回の主案は、**候補を残す場所を一段内側へ移す**変更である。

形式的には、局所の代理利益を g(P)、配置Pを実際に実行して後処理した費用を C(P) とすると、従来の `C(argmax g)` を、上位候補について実行・検査する方法へ広げる。gを真の費用だとみなさず、安い候補生成器として使う。

なお、現在も全候補を完全に後処理するわけではない。後処理前の2／4系統の制限で元の候補が押し出されることもあるし、終状態の価値は近似である。**注文ごと・ケースごとの単調改善保証はない。** 実測の対応比較で判断する。

## 2. 区間DPをK-bestへ拡張する

候補はハンドル区間 [l,c] と、その代理利益gを持つ。区間が交わらない配置を選ぶ元のDPは、ハンドルの境界0〜Hを頂点とするDAG上の最長路として書ける。

- 区間を使わない辺 c→c+1 の重みは0。
- 補助紙候補 [l,c] を使う辺 l→c+1 の重みはg。

頂点jに到達する上位K本の経路を L_K(j) とすると、次を計算すればよい。

```text
L_K(c+1) = TopK( L_K(c)
                  ∪ { p + candidate : candidate ends at c,
                                      p ∈ L_K(candidate.left) } )
```

単純なK-best版も実装し、64件で−0.112643 ± 0.019351% SEだった。ただし、同じ紙を少し違う高さへ挿すだけの候補が上位を埋めやすい。

そこで、各経路に次の列を署名として持たせた。

```text
(kind, column, depth, index, post) の列
```

同じ署名の経路は最も利益の大きいものだけを残し、挿入開始レベルlだけの違いで枠を使わないようにする。通常の候補では列・深さが紙を特定し、古い補助紙やチェーンではkind/indexが対応する。この「系統」はコード上の候補署名であり、異なる表現で同じ実紙列になる全ケースを完全に同一視するものではない。

元の一解DPが選ぶ署名を別途そのまま復元し、それを追加候補から除外する。元の計画はもとの計画探索に残るため、追加枠は別系統へ使える。既存のgainは整数および0.2／0.5刻みなので、系統版では10倍して整数化し、丸め誤差に依存した並べ替えを避けた。

各DP頂点で上位K個の異なる署名を残してよい理由は、固定した最後の候補を付け足す操作が、異なる前方署名を異なる完成署名に写すからである。同じ前方署名の低い利益のものは、同じ境界より右の継続で有利にならない。これはこの区間模型での議論であって、実問題全体の最適性ではない。

同じ再帰を別のPython実装で再現した、小グラフ全列挙との照合を `verify_interval_dp.py` に収録した。C++関数そのものを呼び出す単体試験ではなく、アルゴリズムと同点処理の照合である。ランダム2,000グラフ、14,000個の上位K検査で、利益、署名の一意性、Kを増やしたときの同点処理の整合を確認した。

## 3. どの状態から追加候補を作るか

全ての返却オプションにK-bestを掛けると高い。そこで、元の探索で最良だった二つの文脈に限定した。

1. 通常の返却・再配置計画の最良オプション。
2. 古い紙と新しい補助紙を同じ区間DPで決めるjoint計画の最良オプション。

それぞれを同じ注文開始状態からやり直し、区間DPの第1〜第3追加系統を使う。追加された計画は、既存と同じ実際の可視性・最終表示・384操作上限・補助紙の回収可能性を確認する。その後、既存の `record_future` と後処理へ渡す。

軽量版は3×2＝最大6回の追加計画を作る。実際の操作として6手足すわけではない。候補生成の計算量だけが増え、選んだ1本の操作列だけを出力する。

追加候補が同じ終状態や同じ移動紙列へ収束した場合は、既存の候補の重複除去も働く。Kを7、15、31と広げる実験も行ったが、開発8件では7→15で6手、15→31で1手の上積みに留まった。広げ続ければ大きく改善するという結果ではない。

## 4. 補助紙を全て戻す初期化も緩めた

比較器の間へ商品紙を挟むhelper計画は、従来、前の商品紙と全ての旧補助紙を一旦列へ返してから始める。これでは、既に必要なハンドルを正しい色で覆っている紙まで返すことがある。

`WARM_HELPERS=1` は、通常のhelper計画を残した上で、次の別候補を追加する。

比較器層を分断する旧補助紙は返す。一方、比較器より下にある旧補助紙は、既存の `refill_or_return` を使い、安全に残せるか、別の高さへ直接移せるかを調べる。capと六枚の比較器が計画に必要な連続状態であることを確認し、残した紙で覆われるハンドルを以後の修復対象から除く。

最終的な操作列は常に全表示・全可視性で確認する。局所的に「正しい色だから残してよい」とみなすだけの変更ではない。

最初の8件では40手改善したが、追加24件で57手、さらに新規64件では、候補別ejectionとの組合せでも191手、−0.028722 ± 0.012561% SEに縮小した。これを単独の大改善とは扱わない。

前の商品紙そのものも通常の穴埋めへ流す強いwarm版、helperの取得順序を可視性条件で変える版も試した。前者は明確に優れず、後者は開発8件で基準と同点だった。

## 5. 広探索版の構成と前回版との差

広探索版は、前回の列部分列MDPを0.25で混ぜ、区間DPの追加系統を7×2へ増やし、warm helpersを有効化する。後処理へ残す移動紙列を4系統にし、各候補に2削除＋1修復のejectionも適用してから比較する。

元の処理では、複数候補を通常の削除・差込先変更で比較した後、勝者に主なejectionを掛ける。候補ごとにejectionを先に適用すると、修復で短くなる次点を拾える。ただし、その分CPUを使う。

前回の統合版は `COLUMN_CONTROL=.25 OLD_HELPER=1 POST_CANDIDATES=4`。ここでOLD_HELPERは「前の商品紙を六枚の比較器に混ぜ、最大7!の状態を調べる」前回の機能である。今回のwideは `OLD_HELPER=0` で、代わりに上記の新しい追加計画を使う。**前回版への単純な足し算ではなく、構成全体の比較**である。

列MDP自体の寄与は分けて測った。今回の128件ではMDP単独が−0.085237%で、MDPに系統3候補を加えた純増分は **−0.136698 ± 0.011039% SE、107／1／20**。したがって、主案の利益を前回MDPの再計上だけで説明してはいない。

## 7. 時間とキャッシュ

同じ区間DP入力を各追加順位で解き直す代わりに、必要なKまで一度だけ計算して再利用する版も実装した。キャッシュのキーは候補表全体の厳密比較で、ハッシュ衝突を許容した近似ではない。入力が異なる二つの文脈を誤って共有しない。

新旧5設定×8件の40出力はキャッシュ有無・再構成前後で全バイト一致した。Kの増加で上位経路の同点順が変わらないことも、小グラフ全列挙の14,000検査で確認した。

## 8. 再検討した別の方向

### 二枚cap・三つの無料の持上げ位置

一枚のcapで2窓をまとめて切り替える前回案とは異なり、今回は固定capを二枚にした。上のcapは1ビット、下のcapは残りを担当する。商品紙を両方の上、二枚の間、両方の下へ置く三つの位置を、通常のliftの行き先だけで選ぶ。

商品紙のcap部分をa、要求をb、capの印刷色をCとすると、到達可能性は、上から順に覆うprefix mask mについて

```text
(a & ~m) | (C & m) == b
```

となる。2窓の場合のmは0、1、3。共有ペアの片方から他方へ到達できれば、どちらかを商品紙に印刷できる。独立一様な2bitパターン対の抽象模型では、互換な順序付き対は一枚2窓capの10/16から12/16へ増える。ただし実入力は固定32bit・入力依存窓選択であり、この比率を実入力の互換率や手数改善率と同一視していない。

代償は専用紙が185→184枚、必要な共有ペアが71→72組となること。計画側も二枚capの順序、helperの挿入offset、capを越えない不変条件を変更した。

開発8件ではG36/H26/2窓capが215手改善したが、新規64件では **741手悪化、+0.113471 ± 0.149800% SE、26／1／37**。誤りは0でも、有利な構造と判断する根拠は得られなかった。少数件の改善を採用根拠にしない。窓・cap順・比較器・商品ペアの共同設計には余地が残るが、未検証である。

### 初期順序を無料で選ぶ

設計出力時に紙番号を付け直せるので、初期列を白／黒の重み付きマージで最適化したり、独立の仮想注文で整えた状態から開始する案を実装した。実注文の先読みはしない。

開発8件で、列順のみは9手改善、比較器順も選ぶ版は7手改善。128仮想注文の最良状態は24手悪化、最後の状態は38手悪化、512件版は47手悪化した。初期ポテンシャルを下げることが1024注文の総手数改善に直結するとは確認できなかった。

### その他

| 試したこと | 今回の観測と判断 |
|---|---|
| 全ての操作の挿入先を再探索 | 開発8件で48手悪化。同一列内に絞った追加探索は同点。 |
| 最後の3／4操作を2操作へ修復 | 2件の小さな試行では改善0。全解法の最適性を示すものではない。 |
| ejectionの全挿入時刻／全2削除組 | 8件で基準と同点。 |
| 現在の列頭での複数窓修復利益を終状態価値に追加 | 係数0.5／1.0で8件33／57手悪化。 |
| 比較器の将来費用を全体評価に追加 | 係数0.5／1.0で8件3／5手悪化。 |

| 同点時だけ補助紙の将来費用で選ぶ | 新規64件で459手改善、−0.068897 ± 0.018756% SE。軽量な別案だが、主候補の128件には含めない。 |

全挿入先の再探索が悪いという観測は、最終確認で読んだPR119のreanchorの結果とも同方向だった。PR119では終状態の価値の予測が概ね実際の将来差を説明すると報告されている。この既存の計測を今回独立に再実行したわけではない。

今回の主案も「価値モデルを全て作り直す」ものではない。**その価値モデルで評価される前に、粗い局所DPで消えていた候補を残す**点に焦点を置いている。

## 9. 実験条件と再現

入力はC++ `mt19937_64` のseed 880074000〜880074127で独自生成。各商品は64bit中32bitが1、商品は非復元、注文は直前の商品を除く一様分布。公式Rust版の同番号seedとは異なる。生成時の標準ライブラリ差に備え、入力hashを保存し、再現スクリプトは一致を確認する。実入力と生操作列を含むアーカイブも会話に添付する。

固定した設計の仕事量は以下。

```text
FIXED_WORK=1  NO_FALLBACK=1
MAP_ITERS=262144  GOPT_STEPS=65536
ANNEAL_ITERS=12582912  CLIMB_ITERS=32768
```

FIXED_WORKは大域の期限を無効化し、再割当て・穿孔・helper表を時間切れで欠落させない。注文処理も全1024件で通常処理を使う。提出環境の2秒予算とは別の品質実験である。

```sh
python3 evaluate.py --solver generated/research --checker generated/checker \
  --out runs/reproduction --start 0 --count 128 --jobs 2
python3 verify_interval_dp.py
```

`evaluate.py` は新しい保存先を要求し、入力・設計・stdout・stderr・全結果・hashを残す。共通のpahcer履歴は更新しない。この環境ではRustがなく、**公式Rust testerは実行していない**。独立C++チェッカーと、注文を一件ずつしか渡さないreactiveハーネスを使った。

最終のlean／wideはGCCとClangでビルドした。最終生成ソースで4つのsmoke実行を再確認し、記録した出力と一致した。さらにleanのcase0、wideのcase64を対話形式で実行し、オフライン出力と全バイト一致した。Clangについてはビルド確認であり、128件の評価はGCCによる。配布する `checker.cpp` を再コンパイルし、配布する `evaluate.py` 自体でもcase0の全6方式を実行し、保存済みの出力hashと一致した。

前回統合版の再構成も、元の単独 `column-mdp-reuse-four.cpp` と2件で全stdout一致を確認した。前回の紙構造・設計を変えた別アルゴリズムを比較対象に紛れ込ませてはいない。

## 10. 現行mainへ移植するときの優先順位

最初に試すのはleanの三箇所、すなわちK-best区間DP、最良normal／joint文脈からの追加計画、既存候補・後処理への接続である。設計段と列MDPの定数は触らない。

現行mainは esw-climb4／esw-colmdp 系で、既に別の後処理・高速化・ペース制御・操作ラベルを持つ。古いmain.cppを丸ごと置き換えず、`OP_TAG`の操作列との対応、DesignStore、effortの扱いを保って移植する必要がある。**最新mainへの追加効果は、このPRの数値から直接には分からない。**

次に計測する価値があるのは、追加順位、代理利益の差、実行前後の候補の順位、後処理で減った手数である。ほぼ同じ結果になる文脈や、大きく劣る局所候補を安く省ければ、利益を保ったまま広探索の費用を減らせる可能性がある。

また、追加候補によって後処理前の上位枠から元の良い候補が押し出される問題も残る。元の候補を保護した候補枠や、後処理後に枠を絞る方法は次の仮説であり、今回は実装・成績を報告していない。

今回確認できたのは、紙構造を固定したまま局所DPの候補消失を減らす **約0.14%の独立した改善**と、その周辺機能を組み合わせた **前回統合版比約0.24%の品質改善**である。広探索を2秒に収める作業と、最新mainでの再測定は別に必要である。
