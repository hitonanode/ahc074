# 階段型ビーム構築 v2：実装・検証報告

## 到達点と比較範囲

提供されたZIPの入力0000–0099を、各方式の設定を固定して検証した。各100ケース、102,400注文。

|方式|総手数|平均手数/注文|表示誤り|不正操作|
|---|---:|---:|---:|---:|
|元の esw-clean.cpp|1,033,546|10.09322265625|0|0|
|staircase_beam_v2.cpp|1,036,371|10.12081054687|0|0|

新版は元の既存解より **0.02758789062手悪い**。ケース単位では45勝55敗。
前回のビーム版の16.01297手は前回会話の報告値であり、今回再実行した結果ではない。
今回の版は既存最良を更新しておらず、9.5手にも届いていない。

**実装上の重要な限定：全192枚を自由な三値パターンとして上からビーム設計したものではない。**
既存解の6枚の共用比較層、窓割り当て探索、合法なオンライン操作器を再利用した。
主対象は階段に収納する185枚であり、互いに共有可能な目標を含む紙群を、上の段から局所的にビーム再構築する。
その後、既存の列配置調整を短く実行するハイブリッドである。

## 出力を観察して分かったこと

既存解は、38窓を6枚の共用紙に受け持たせ、取り出し用の階段を25段にしている。残り1窓はcap。
100ケースで紙の内訳は毎回、共用6枚、cap1枚、単独目標用114枚、2目標共有用71枚だった。
塗られたbit数の平均は、共用紙12.6667、2目標紙37.4418、単独目標紙55.1601。

つまり、少しずつbitを埋める紙を大量に持ち上げて完成させるのではなく、密な主紙を1枚選び、
残った穴を常駐する共用層と階段の色で補う。階段の先頭紙を利用できるので、
目標の64bit全部を新しく選んだ紙で被覆することは、実手数のよい代理目標ではなかった。

階段の各段の収納枚数も均等ではない。seed 0の既存解では浅い段が3枚程度、深い段が12枚程度。
深い段ほど印刷可能なアクセス窓が多く、穴が少なくなる一方、同じ段への詰め込みは掘り出しを重くする。
この両方を評価する必要がある。

## 新構築

### 1. 階段の枚数配分を動的計画法で決定

標準設定は37窓の共用層と26段のアクセス階段。capを合わせて64窓となる。
段cの紙枚数をn、うち2目標共有紙をpとすると、深さの重み付き合計の近似は

    (n*(n-1) + p*(p-1))/2

であり、これに残った下側アクセス窓の修復費用

    0.38 * (n+p) * (H-1-c)

を加え、紙185枚・共有71組を段に配分する。白黒双方の先頭紙を確保する割り当てで初期化する。
割り当てが不可能なら、元の実行可能な初期配置を保持する。

### 2. 関連する12枚を上からビーム再構築

無作為な紙群では、交換できる共有目標が少ない。そこで共有可能性グラフをたどって紙群を集める。
ビーム状態には、割り当て済み目標のマスクと、処理中の段の色・共有枚数を持つ。
1枚の候補を、残っている1目標または2目標から作る。2目標の場合は、その段で印刷可能な位置のうち一致するbitを塗り、異なるbitを穴にする（cap窓は既存の特別処理を使う）。
共用窓の残余が比較層で解けることと、自分のアクセス窓で両目標の色が一致することを必須にする。
単独用・共有用の区分や先頭色を元の紙のまま固定しない。

段を完成したときに、その段の掘り出し費用を評価する。残余bitについては、穴の修復費用、
共用層の変更費用、他の目標を修復する補助紙としての価値を使う。単純な被覆bit総数では評価しない。
既知の実行可能な経路をビーム内に保持し、枝刈りによる完成不能を防ぐ。
標準は幅64、1回12枚、400回。候補の最終採否は代理評価の全体再計算で決める。

### 3. 短い配置調整と既存オンライン処理

元の約1490万回の配置焼きなましを、標準200万回に短縮して併用する。
主紙の具体的な塗り方は目標と段から導出し、注文処理・可視性を保つ操作列の生成は既存器を使う。
元のご提案の「寄与bit下限を段階的に増やす」をそのまま残すのではなく、
紙の候補を密な主紙に制限し、残余の完成費用を評価に入れる形に変更している。

## アブレーション：同一の20ケース（seed 20–39）

|設定|平均手数|
|---|---:|
|ビームだけ無効（CB_PRE=0）|10.13549804688|
|新版の標準設定|10.10771484375|
|配置焼きなまし・climbを無効|10.38911132813|

この20ケースでは、ビームの追加効果は0.02778320手にとどまった。
大きな改善は構造・役割分担の変更によるもので、ビーム自体が既存探索を圧倒したとは言えない。
焼きなまし無効版でも、窓割り当て探索と最後の再マッチングは残っている。「全工程が純粋なビーム」の意味ではない。

## 残っている差

既存解→新版の1注文あたり操作内訳は、主紙の掘り出しが2.87534→2.79806、
共用層の変更が1.23686→1.20939と減少した。一方、fixが1.74274→1.80978、
repairが0.81586→0.83646、補助紙の戻しが1.13006→1.14887と増えた。
取り出し側で得た利益が、アクセス窓の修復と補助紙の往復に相殺されている。

## 検証と実行時間

Pythonの独立チェッカーで、全操作について選択紙が少なくとも1窓で見えること、
挿入位置と操作上限、最終表示、余分な出力がないことを検査した。公式Rustテスタを実行した結果ではない。
さらにseed 0,19,42,73,99では、設計を受信するまで注文を一切送らず、各注文を1件ずつ渡す対話検証を行った。
全5ケースが誤り・不正操作0で、出力は一括入力による検証時と完全一致した。

LOCAL_BENCHなしの単独実行15ケースでは、内部経過時間は平均1.787684秒、最大1.893680秒。
0ケースで2秒を超えた。**2秒制限内を保証する提出版ではない。時間対策が必要。**
100ケースの並列検証時の時間は、単独実行の目安として使っていない。
