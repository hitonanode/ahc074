# AHC074: 上からの残余bit被覆ビーム構築

## 結果と現時点の位置づけ

既存の `esw-clean.cpp` の構築・ペアリング・比較器を使わず、新規に書いた実験実装です。

固定した最終設定を、添付ツールの `in/0000.txt` ～ `in/0099.txt` の100ケースで評価しました。

| 項目 | 結果 |
|---|---:|
| 注文数 | 102,400 |
| 総操作数 | 1,543,793 |
| 平均操作数/注文 | **15.076103515625** |
| 表示誤り | **0** |
| 不可視の紙の移動などの不正操作 | **0** |
| 1注文の最大操作数 | 42 |
| ケース別平均の最良 / 最悪 | 14.509765625 / 15.6435546875 |
| 調整に使わなかった seed 5～99 の平均 | 15.07271792763158 |

**既知の10.10手を更新する結果ではありません。** この構築方針の実装、評価、再現のための実験版です。

### 重要な区別: 構築時の被覆と、実行時の完全一致

構築では、目標ごとの未被覆マスクを持ち、寄与下限を満たす紙だけをその目標に採用します。
ただし、**最終設定は、192枚を決めた時点で、この採用履歴だけによる全目標の完全被覆を必須にしていません**。
残ったbitは、実行時に同じ階段列の先頭紙を0/1に切り替えることで埋めます。別の既存解法へ切り替えるものではありません。

代表例seed 0では、構築の採用履歴が埋めたのは16,384個の「目標×bit」のうち10,198個で、6,186個が残っています。
その残りも実際の操作数に含めて、全注文で表示一致を検証しています。したがって「残りを無視した推定15手」ではありません。
一方、「採用紙だけで全目標を埋め切る純粋な構築が15手で完成した」という意味でもありません。

## 使い方

```bash
g++ -O3 -march=native -std=c++20 topdown_beam.cpp -o topdown_beam

# 保存済みの入力を使った実行。通常のreactive入出力にも対応しています。
./topdown_beam < results/input_0000.txt > answer.txt

# 添付のYAAu43G9.zipを展開した tools/in を指定します。
python3 benchmark.py --solver ./topdown_beam --inputs /path/to/tools/in \
  --results reproduced --seeds 0:100 --workers 4

# 注文を1つずつ渡す対話検証。未来の注文を解答側に渡しません。
python3 benchmark.py --solver ./topdown_beam --inputs /path/to/tools/in \
  --results interactive_check --seeds 0,50,99 --workers 1 --interactive
```

コンパイル後のプログラムは、最初の256商品だけを読んで紙を設計し、192枚を出力・flushしてから、注文を1つずつ読みます。

## 構築

### 1. 階段状の保管構造

64段の列を作ります。列 `c` の紙は、bit `c` が必ず不透明で、bit `c+1..63` は必ず穴です。
bit `0..c-1` は自由に白・黒・穴を設計します。列は `0,1,...,63` の順に並びます。

各列には、自分のbitが白の紙と黒の紙を最低1枚ずつ置きます。各列の最低2枚に加えて64枚を配分し、全体で192枚にします。
実装は累積枚数の目安 `round(192*((c+1)/64)^SHAPE)` を使い、各列最低2枚・残りの列にも最低2枚を残す条件で丸めています。

この条件から、列cの先頭紙は必ずbit cで見えます。前にある列はすべてbit cが穴だからです。
先頭紙を同じ列の下へ差し込めば、次の紙を合法的に取り出せます。
すべての移動紙を列に戻した状態なら、各列の先頭を目標の色へ合わせるだけで、任意の64bit目標を正確に表示できます。

### 2. 目標ごとの残余

目標tについて未被覆マスクを `R[t]` とします。
紙の不透明マスクを `O`、黒マスクを `B` とすると、採用条件は次のとおりです。

```text
((A[t] XOR B) AND O AND R[t]) == 0
popcount(O AND R[t]) >= tau(c)
```

前者は、未確定位置に誤った色を出さない条件です。既に上の紙が埋めた位置の色は問いません。
後者が寄与下限です。ただし、その紙で残余全体が完成する場合は、下限未満でも採用可能にしています。

採用したときにだけ `R[t] &= ~O` と更新します。
同じ目標が同じ保管列から複数枚使うことは、構築中は禁止しています。

### 3. 二重のビーム

**外側のビーム**は、決定済みの紙列、256目標の残余、採用履歴を状態にして、紙を上から1枚ずつ増やします。既定幅は2です。

**内側のビーム**は、その紙の模様を探索します。目標の未被覆位置だけを色の制約に使い、ある位置で白・黒の要求が衝突するなら穴にします。
追加の位置・色の制約で対象目標集合を絞り込み、より濃い紙も候補にします。幅12、最大18段です。
単一目標に特化した候補も常に用意します。

下限未満の部分状態をすべて評価0にすると、下限へ達する前に探索が区別不能になるため、内側ビームの途中評価だけには弱い値 `0.2*g` を与えます。
これは完成候補の正式な寄与、残余更新、採用枚数の計数とは別です。

### 4. 最終設定の評価

```text
tau(c) = round(5 + 15*c/63)
```

採用目標について、基本的に `新しく埋めるbit数 - 6` を評価します。残余全体を完成させる場合には5を加えます。
「6」は実操作を6回と決め打ちした値ではなく、1目標に多数の紙を採用することを抑える設計時の罰則です。

外側では、対応する累積値、すなわち

```text
未被覆bit数の合計 + 6*採用回数 + 5*未完成目標数
```

を小さくする候補を残します。

## 実行時の手順

構築時の採用履歴をそのまま毎回全部持ち上げるだけでは、取り出し・差し戻しが高くつきました。
最終実装では、商品一覧だけを使って事前に短い前面の紙列候補を探索し、注文時に次を比較します。

1. 選んだ前面の紙列でまとめて覆う。
2. まだ空いている位置に対して、紙を必要な段の直前へ差し込み、正しい色になる区間を覆う。
3. 残りは列の先頭の色を合わせる。

区間候補は、現在の列の深さと先頭の色から、実際に省ける操作数を評価して区間DPで選びます。
選択した操作列については、操作の削除も試し、毎回、最初の重ね順から合法性と最終表示を再検証します。
いずれも未来の注文は使いません。

## 試行錯誤: 先行5ケース

次はseed 0～4だけの比較です。最終100ケースの平均と混同しないでください。

| 設定 | SHAPE | 外側幅 | 平均手数 |
|---|---:|---:|---:|
| 下限3→8、採用罰則なし | 2.0 | 2 | 21.7765625 |
| 下限5→16、採用罰則なし | 2.0 | 2 | 16.386328125 |
| 下限6→24、採用罰則なし | 2.0 | 2 | 15.2984375 |
| 下限を12で固定、採用罰則なし | 2.0 | 2 | 15.743359375 |
| 下限5→20、採用罰則6 | 2.0 | 2 | 15.2119140625 |
| 下限5→20、採用罰則6 | 2.0 | 1 | 15.1296875 |
| 下限5→20、採用罰則6 | 2.0 | 4 | 15.14375 |
| **最終設定: 下限5→20、採用罰則6** | **2.5** | **2** | **15.1404296875** |

この比較では、低い下限を上げる効果は大きい一方、ビーム幅を広げるだけでは一貫した改善を確認できませんでした。
また、採用されない低寄与目標を候補の色制約から外す変種 `PRUNE=1` も試しましたが、最終設定には採用していません。

初期の試作には、構築採用履歴だけで全64bitを完成させる設定もあります。
しかし、多数の紙を使うことと、その取り出し費用が問題となったため、最終設定では上記の列先頭切り替えを併用しています。

## 検証の範囲

`benchmark.py` は、解答内部のassertとは別に、出力された全操作について可視性・添字・操作回数を検査し、各注文後の64bit表示を再計算する独立Pythonチェッカーです。
添付された公式ツールの入力100ケースを利用していますが、公式Rustテスタそのものの実行結果ではありません。

- 100ケースすべてで、全操作の合法性と全102,400注文の表示一致を検証しました。
- seed 0, 50, 99では、未来注文を渡さない対話形式も独立に検証しました。3,072注文で誤り・不正操作とも0です。
- seed 0～4をパラメータ比較に使いました。残り95ケースは最終設定を固定した後に評価しました。

## 実行時間

ローカル単独実行のseed 0～4では、プログラムの経過時間は平均1.77204秒、最大1.89728秒でした。
100ケースの4並列評価では平均2.14252秒、最大2.47899秒です。後者は同時実行の負荷を含むため、単独実行の制限時間判定には使えません。

対話検証の経過時間にはPythonチェッカーの処理待ちも含まれます。
AtCoder本番の2秒制限内で安全に動くことは未確認で、時間打ち切りによる探索縮小も未実装です。
現時点では性能・実行時間の両方について、そのままの提出を推奨するものではありません。

## 主な調整用環境変数

| 変数 | 既定値 | 意味 |
|---|---:|---|
| `OUTER` | 2 | 紙列を構築する外側ビーム幅。1は逐次貪欲に相当 |
| `BW` | 12 | 1枚の模様を探索する内側ビーム幅 |
| `DEP` | 18 | 内側の探索段数 |
| `BRANCH` | 4 | 各構築状態から出す紙候補数 |
| `T0`, `T1` | 5, 20 | 寄与bit下限の始点・終点 |
| `TPOW` | 1 | 下限の増加曲線の指数 |
| `PEN` | 6 | 1目標への紙採用1回の罰則 |
| `BON` | 5 | 残余全体を完成させる目標への加点 |
| `SHAPE` | 2.5 | 深い列へ多く配分する累積枚数曲線の指数 |
| `PRUNE` | 0 | 内側探索で低寄与の対象目標を色制約から外す実験 |
| `QBW`, `QLEN`, `QALT` | 32, 6, 10 | 前面の紙列候補の探索幅・長さ・保持候補数 |
| `FRONT` | 1 | 前面の紙列候補を使う。0は区間パッチだけ |
| `POST` | 1 | 実操作の削除・再検証を行う |
| `PROFILE` | 未設定 | 指定ファイルへ紙ごとの構築統計CSVを出力 |
| `VERBOSE` | 0 | 列ごとの構築進捗をstderrへ出力 |

例:

```bash
T0=3 T1=8 PEN=0 SHAPE=2 ./topdown_beam < results/input_0000.txt > low_threshold.txt
T0=6 T1=24 PEN=0 SHAPE=2 ./topdown_beam < results/input_0000.txt > higher_threshold.txt
PROFILE=profile.csv ./topdown_beam < results/input_0000.txt > answer.txt
```

- `results/input_0000.txt`, `output_0000.txt`: 再現用の入力と最終設定の出力。
