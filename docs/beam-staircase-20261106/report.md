# AHC074 階段型ビーム構築・改良の研究記録（2026-11-06）

> 研究用の記録。**現時点の提出推奨版ではない。** 主たる比較対象は、調査開始時に提供された `esw-clean.cpp` であり、このリポジトリのその後の最良解を意味しない。初期の独立ビームと、既存の比較器・注文処理を再利用するハイブリッドを混同しない。

## 0. 目的と条件

- AHC074 A: 64窓、192枚の紙、256目標、1024注文。紙は初期設計後に変更できず、注文は未来を読めない。
- 操作は現在見えている紙を1枚取り出し任意深さに挿すこと。誤り1注文のペナルティは384手なので、全試作で表示誤り0を目指す。
- もとの依頼は「階段状の紙を**上から**順番にビームサーチで決め、目標ごとの未被覆bitをできるだけ多く覆い、寄与bit数の下限を後半ほど上げる」ことだった。
- その後、既存解の実際の出力から段数・紙の密度・掘り出し・返却を観察し、初期の純粋な方式に固執せず設計を段階的に変更した。

## 2. 最初の64段・上からの残余bit被覆ビーム

### 構造と条件

- 64段、各列cの紙はbit cを必ず0/1で印刷し、それより後方のbitをすべて穴にする。各列に0/1両色を確保し、目標を必ず完成できる。
- 目標tの未被覆マスクR[t]、候補紙の不透明O・黒Bについて、未被覆部分の色衝突がなく、`popcount(O & R[t]) >= tau(c)` の時に寄与とする。ただし残余全体を埋め切る候補は例外。
- 下限は序盤から終盤へ `tau(c)=round(5+15c/63)` と増やす。採用を1回増やすごとに6の罰則を設け、小寄与紙の濫用を抑える。
- 外側のビーム（既定幅2）は紙列・256目標の残余・採用履歴を保持。内側（幅12、最大18段）は対象目標の集合を絞り、白黒衝突位置を穴にした1枚の紙を探索する。
- 採用履歴のみで全目標を完全被覆させたわけではなく、残余は注文時に階段列の先頭を回転して埋める。この補修も操作数に含めた。

### 結果と診断

- 100ケースで平均15.0761手、誤り0・不正0。seed0では採用履歴の完成bitが10,198/16,384、残余6,186bit。
- seed0の前半48枚は平均9.69bit、後半48枚は57.79bit印刷、寄与する目標数の平均は前半3.68→後半1.60。疎→密への傾向は確かに生じた。
- 1注文あたり返却3.1618、掘り出し2.6489、配置3.2422、残余列先頭の補修6.0231手。追加の修復費用が大きい。
- seed0〜4の先行比較では下限3→8（罰則0）で21.7766手、5→16で16.3863、6→24で15.2984、下限固定12で15.7434。下限の増加は効果的だったが、被覆量を最大化するだけでは実操作を十分に減らせない。

## 3. 既存の出力を観察し、26段＋共有層へ（v1）

### 観察事実（100ケース）

- 参照解法は階段を25段に絞り、38窓を6枚の共有比較器、1窓をキャップに割り当てている。
- 主紙の不透明部分の平均は単独目標用55.16bit、2目標共有で37.44bit。表示完成時、最上位の商品紙は平均45.20bitを実際に表示し、共有紙が担当するのは平均6.89bit。
- 64段で最初の紙が薄いのは「上から決定する」ための必然ではない。全64窓を取り出し口にした制約によって、上側が印刷できる範囲が狭くなっていた。

### 変更

- 窓を共有37、階段26、キャップ1とし、紙を共有6、キャップ1、商品主紙185とする。
- 商品紙185枚は単独目標114枚と2目標共有71枚。256目標に主紙を1枚ずつ割り当て、共有ペアの不一致位置を穴にする。
- 比較器の6紙の上下関係で残余を表現できることを、要求される有向辺のDAG判定で保証する。
- ビームは主紙1枚の局所被覆を選ぶのでなく、次のハンドル順を確定するたびに残り全体の割当をハンガリアン法で構成・評価する**完成割当ビーム**に変更。
- 評価は、使用頻度付き取り出し深さ + 残余の色補修期待費用 - 補助紙価値。これは非線形目的関数の厳密な下界ではない。
- 共通比較器・共通窓割当探索・目標再割当・オンライン注文処理は参照解法の既存実装を再利用した。**純ビームだけの結果ではない**。

### 実測

- v1は100ケース平均10.2638手。64段版を100/100ケースで上回ったが、参照版10.0932手には及ばなかった。
- 主紙掘り出しがv1 3.0661 vs 参照2.8753手、約+0.1907手で、総合差+0.1706手の主要な所在。
- G/Hを38/25、36/27、37/26とした5ケース調整では37/26・幅2・分岐5が10.1891手で最良。段数が少なければ良いわけでもない。
- 薄い専用共有紙を足す試作は紙の予算・配置・差し戻しで不利となり、既定経路では使用しなかった。

## 4. 固定容量の制約を外し、構造の連動探索へ（v2）

### ボトルネック

- v1の各列容量は全ケースで `2,2,2,3,3,3,4,4,5,5,6,6,7,7,8,8,9,9,10,10,11,11,12,12,13,13` に固定。
- 後方約1/4の列の使用時、主紙掘り出しはv1 4.3854 vs 参照3.9780手。後方の単独主紙初期深さも7.5258 vs 6.6439。
- もっと濃く印刷できる後方列へ詰め込みすぎると、取り出しで損をする。密度を上げるだけでは改善しない。

### 変更と結果

- ビームで実行可能な完成案を作った後、列容量・ペア・目標所属・ハンドル順序を一体で動かす既存の連動焼きなましへ渡す（品質優先：14.9M反復）。補助紙価値を反映した列交換と4回のハンガリアン再割当を続ける。
- 100ケースでv2品質優先10.0968555手、v1比0.16697手の削減（91勝9敗）。参照版には49勝51敗、平均0.00363手負け。
- 掘り出しはv1 3.0661→v2 2.7917（-0.2744）、色補修は1.7563→1.7562、共有紙移動は1.2228→1.2061。その他が4.2186→4.3428へ増え、利得を相殺。
- 最上位主紙の実表示bit数は45.6430→45.0787に**減っても**手数は改善。被覆を増すだけの構築評価は不十分。
- 軽量版（`-DBEAM_FAST=1`、初期幅1・分岐3・連動反復4M）は100ケース平均10.1197手。単独6ケースで平均1.8065秒、最大1.8901秒。ただし本番時間保証なし。
- 設定確定後の別の30ケースはv2品質優先10.0819、v1 10.2520、参照10.1239。v2と参照の差は小さく、正規近似95%区間は0を含む。

## 5. 補助紙利用可能性の検証と後処理（v3）

### 採用した変更

1. 参照解法に既存の `Perforation` をv2では呼んでいなかったため、主紙の取り出し口以外の印刷bitを少数だけ穴にする処理を復活（重み0.5）。主紙の補助価値と自分の残余補修費用を比較する。
2. 複数の完成手順候補をより深く修正（`PLAN_LIMIT=4, REFINE_BEST=2, NS_ROUNDS=4, NEUTRAL_WIDTH=8`）。既存探索の計算配分を増やした。
3. 3操作をまとめて削除して1操作で修復する局所近傍を追加。修復紙を動かせる可視性と表示を操作列全体の再生で確認してから採用する。

### 効果の内訳

- 10ケースのアブレーション（同じv2構築）: v2 10.07246、穴あけのみ10.05615、深い手順探索のみ10.06357、3削除→1修復のみ10.07031、組合せ10.04854手。
- 3削除近傍単独の寄与は約0.002手。0.02手の改善をすべてこの新しい近傍の成果とはみなせない。
- 100ケースでv2→v3は平均0.01974手削減、77勝2分21敗。v3の100ケース総操作数は1,031,897。
- v2との印刷パターン差は100ケース平均4.95箇所/4.54枚で、印刷済みを穴にする変更だけ。

### 不採用になった構造・操作の試作

| 試作（主に調整用seed 0〜4） | 平均手数/注文 | 結果の読み方 |
|---|---:|---|
| v2対照 | 10.0465 | 小規模調整集合 |
| 物理的重ね順を状態に持つ補修ビーム | 10.0531 | 後処理を超えず |
| 古い補助紙を維持し邪魔なものだけ動かす | 10.0469 | ほぼ同等 |
| 仮想次注文32個で終了状態評価 | 10.0539 | 実際の未来注文は読んでいない |
| 共通7枚・40窓/階段23段 | 10.1906 | 5040順列を検討した設定 |
| 補修専用紙8枚追加の最良試作 | 約10.347 | 共通35窓・階段28段なども同時変更 |

- 補修専用紙8枚の試作のseed0では、操作ラベルで主紙掘り出し障害として186回、補助紙配置として1回しか使われなかった。単なる有効bit数では「実際に安く取り出せる頻度」を捉えられない。
- 7枚共通層も薄い共有紙も、今回試した構築・評価・予算では改善しなかっただけで、方式一般の不可能性を示したわけではない。
- 実操作を反映する構築評価には `使用可能頻度×補修利益 − 掘り出し・返却・他紙への障害費用` が必要。v3でそれを完全に構築へ組み込めたわけではない。

- 壁時計測定は各報告時のローカル単独実行。AtCoder本番Xeon/2秒制限の保証ではなく、原実験のケース数や時計設定も異なるため速度の絶対比較には注意。
- 特にv3は2秒を大幅に超過し、時間打ち切りがない。**このまま提出すべきではない。** v3の `BEAM_FAST` 設定は今回の130ケースで未検証。
- 全100ケースについて独立Pythonチェッカーで紙・操作可視性・範囲・384手制限・表示の一致を確認。v3追加30ケースも同様。seed0/50/99は未来注文を渡さない対話検証でも3,072注文、誤り0・不正0。
- 公式Rustテスタ・このリポジトリの `scripts/pahcer_run.py` を今回の会話内の比較に使用していない。正式採用には、同時比較2000ケース・壁時計・エラーの再検証が必要。
- 研究コードとして`g++ -O2 -std=c++23 -march=native -fsyntax-only`を4ソースで確認（今回のGitHub記録作成時）。初代の独立ソースは `<bits/stdc++.h>` を含み、リポジトリのClang移植性規約には未対応。アーカイブの原本を保つため未改変。
