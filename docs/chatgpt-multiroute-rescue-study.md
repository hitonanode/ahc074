# ChatGPT: 疎な救済層と複数経路の設計・検証

## 結論

**今回の実装は `imp-910` を上回らなかった。** 最も今後を調べる価値がある案は、比較器6枚に疎な補色の紙2枚を加える「救済層」である。新規生成・設定調整に未使用の64ケースでは、固定模様版が **+1.709 ± 0.190%**、入力ごとの模様学習版が **+1.814 ± 0.210%** 悪化した。差はケースごとの自然対数スコア比の平均×100、±は標準誤差。小さい方が良い。

成果は、表示能力を広げた合法な実装、表示可能性の高速な厳密判定、操作数のどこで損をしているかの測定である。完成版の置き換えや、将来の優越を保証するものではない。複数経路の3案も実装したが、今回の構成では採用する根拠が得られなかった。

基準は `6a7230df96249fca4e789aa0192694adbbbaf084` の `solutions/imp-910/main.cpp`。このファイルの Git blob は `2e2dbbdf132e4c8368d64b226612bfc47ae14c6c`。基準と候補を同一入力・同一環境で比較した。この環境での基準は約10.73手/注文であり、手元の約10.62手と直接比較しない。

## 1. 提案の中心: 比較器だけの汎用層を部分被覆の紙へ広げる

既存解法の汎用層は6枚の比較紙の順序を使う。比較器だけの構成では、共有紙の穴で要求される各色が紙の先後関係になり、その整合性が共有可能な商品対を制限する。

今回の構成は次のとおり。

- 汎用窓36個のうち35個を比較器に使い、1個を救済紙の専用アクセス窓にする。取っ手窓28個は維持する。
- 比較紙6枚に、同じ支持集合で色が補色の救済紙2枚を加える。既定の支持集合は35窓中8窓。専用アクセス窓にも両紙が色を持つ。
- 残る専用紙は184枚。256商品を覆うため、72枚を2商品共用、112枚を単独商品用にする。元の70対・116単独から、共有対が2対増える費用も支払う。

全35窓を塗る救済紙では、それより下の比較紙の順序を隠してしまう。疎にすると、救済紙が覆わない窓では下側の比較器も使える。この部分被覆が設計の要点である。

### 全表示を10080状態で扱える理由

救済紙2枚の不透明窓は同じなので、下側の救済紙は上側の救済紙に完全に隠れる。任意の8枚の配置について、下側の救済紙だけを最下段に置いた配置を考えても、汎用層の表示は変わらない。したがって、上側の救済紙の色2通りと、比較紙6枚・上側救済紙の7枚の順列を列挙すれば、全表示を網羅できる。

\[
2\times7!=2\times7\times6!=10080.
\]

これは10080種類の異なる表示があるという意味ではない。また、不可視な下側の救済紙を実際に動かせるという意味でもない。表示の同値性を示す配置上の変換である。

実装はこの形をcanonical状態とし、実際の不透明窓から可視性を検査して合法な1手の辺を列挙する。要求する部分表示を満たすすべての状態を始点に逆BFSし、その表を `(要求, 穴集合)` ごとにキャッシュする。非canonical配置からは、必要なら可視な上側救済紙を最下段へ送る1手で入る。

**表示能力は8!全配置を網羅する一方、手順の最短性はcanonicalグラフ内に限る。** 非canonical配置を途中に使う、全40320配置上の最短手数は保証しない。

### 表示可能性は順列列挙なしでも厳密に判定できる

上側の救済紙の色を固定すると、表示に有効な紙は7枚。要求色を \(T\)、まだ覆っていない要求窓を \(H\)、紙 \(p\) の不透明窓を \(O_p\)、黒い窓を \(B_p\) とする。次を満たす紙を1枚選んで上に置き、\(H\leftarrow H\setminus O_p\) とする。

\[
O_p\cap H\ne\varnothing,
\qquad (B_p\triangle T)\cap O_p\cap H=\varnothing.
\]

適格な紙のどれを選んでもよい。正しい順序が存在するなら、その紙を先頭へ移しても、その紙が覆う窓は正しい色になり、それ以外では残る紙の相対順序が変わらない。逆に、正しい順序が存在するなら、未被覆窓に最初に触れる紙は必ず適格である。したがって要求が残っているのに適格な紙がなければ不可能であり、貪欲法は完全である。

救済色2通りをそれぞれ元の要求集合から試す。専用アクセス窓が要求に含まれる場合は、その色に限定する。現在の構成は要求窓を必ず紙で覆える。一般の紙集合に適用する場合は、どの紙にも覆われない窓が背景の白になることを別途扱う。

この交換論は比較器や救済紙に限定されない。今後、汎用紙を一般の「白・黒・穴」の模様として探索するときにも使える。ただし、厳密なのは表示の存在判定であり、費用推定や最適な商品マッチングではない。

すべて `main.cpp` 1ファイルで完結するC++23。各ディレクトリのREADMEには、改良元、近似、時間配分、環境変数、診断値を記載した。

学習版は比較器の窓割り当てを先に決め、その後で救済支持窓の交換と色反転を、0.14倍率補正秒・最大400候補で探索する。全64窓のHamming距離26以下の商品対を

\[
0.65d_{\rm handle}+0.28d_{\rm generic}+0.04d_{\rm all}
\]

で並べ、商品が重ならない72対を貪欲に選んだ費用を目的にする。辺の総数だけを増やすと、特定の商品に集中した辺を過大評価するためである。支持窓数は8のままで、最良の模様を保持する。最適matchingや実際の操作数を求めているわけではない。

救済版の通常の設計費用は、goal数を \(q\) とする `0.35 * log2(10080/q)` の代理値。旧6枚専用のhelper interleaveは無効化しており、通常の取っ手穴埋めは使う。比較器だけを前提とした窓割り当て、代理費用、helper未対応は現在の限界である。

## 3. 共有可能性の調査: 増えた候補をスコア改善と混同しない

練習用4ケース `10000..10003` の、全64窓の距離26以下の商品対、計13921対を調べた。比較紙は同じケースの既存解法から抽出し、fixtureと入力のハッシュを保存した。

ここでの「共有可能」は、汎用窓について両商品の部分表示を実現できるという意味。列・取っ手の制約や、商品を重複させないmatchingまで含めた設計全体の成立を数えたものではない。

| 構成 | 共有可能な対 | 比率 |
|---|---:|---:|
| 元の6比較紙・36窓 | 799 | 5.740% |
| 35比較窓＋独立アクセス窓だけ | 891 | 6.400% |
| 全35窓を塗る救済紙、固定ランダム色 | 901 | 6.472% |
| 8窓だけを塗る救済紙、固定ランダム色 | 1179 | 8.469% |

疎な8窓版は独立アクセス窓だけの構成より **32.3%多い互換対、平均72対/ケース増**。これは4ケースで模様を選んだ設計上の指標であり、得点の32.3%改善ではない。実際に必要な72対を頂点重複なしで選べるか、その操作が安いかは別問題である。

全35窓を塗る場合、一意な表示数の上限は

\[
2(1+6+30+120+360+720)=2474
\]

にとどまる。疎な8窓版はこのfixtureで平均約4800表示だった。また、**全35窓を塗る場合に限り**、救済色を元の比較器の表示からコピーしても、アクセス窓以外の表示能力は増えない。下の比較紙をその表示を作る順序で並べれば同じ表示を再現できるためである。疎な支持集合へこの主張を一般化しない。
各比較窓は2枚の比較紙の先後で色が決まるため、比較紙の順序をすべて逆転すると表示も補色になる。したがって補色側の救済紙についても同じ再現が可能である。

3商品共用も調べた。4ケース×比較器2種×救済構成23種の184構成について、距離制限のない全32640商品対から互換グラフを作り、延べ21508三角形を検査した。汎用36窓のうち3商品で色が揃わない窓を共有紙の穴としたとき、その穴を3商品すべてについて汎用層で補える例は0件だった。一般的不可能性の証明ではないが、この構成で3商品共用を主な伸びしろとする根拠はない。詳細と全CSVは [`rescue-feasibility`](../solutions/chatgpt-eval/rescue-feasibility/README.md) にある。

## 4. 評価方法

- 新規ケースは `generate.py` で10000以上10080未満の80件を生成。10000..10015を練習に使い、10016..10079の64件はソルバのソース・設定を固定した後に評価した。holdoutの結果を見てアルゴリズムや設定を変更していない。
- PythonのMT19937で、256個の重複のない32-of-64パターンと、直前と異なる1024注文を生成。指定と同じ分布だが、公式ChaCha20の同番号seedと同じ入力ではない。80件の入力SHA-256を保存した。
- 既存 `scripts/pahcer_run.py` の同一seedでの回転実行順、比較、記録を使用。通常比較は2並列、反復数固定の比較は1並列。GCC 13.3.0、`-std=c++23 -O2 -DCLOCK_SCALE=1.1`。
- Rustコンパイラが利用できなかったため、公式 `tools/src/lib.rs` の仕様を実装したC++対話アダプタを使用。未来の注文を解法に渡さない。全操作を既存 `scripts/replay.py` で独立再生し、可視性・完走・スコアを照合した。公式Rustテスターを実行した結果ではない。
- 時間はこの環境でテスターの起動から終了まで測った壁時計時間。再生検査時間は除く。`CLOCK_SCALE=1.1` は既存設定を維持した値で、このクラウド環境をAtCoderへ較正した値ではない。実機でのTLE余裕は保証しない。
- 得点は `384E+T`。掲載したケースはすべてE=0なので、平均手数はT/1024。比の統計は各ケースの `log(candidate/baseline)` を用い、差が2標準誤差未満なら優劣を判断しない。

途中のファイルへ直接出力を保存する旧収集方式では、採点器が返した最終得点と、再読込した不完全な出力が一致しない事例を確認した。該当する開発用run全体は最終集計に使わず、stdout/stderrをパイプで最後まで収集する方式に修正して同じ固定ソースで再実行した。スコアの良し悪しによるケース除外は行っていない。最終3比較群は280ケース実行すべてで検査に成功した。

### 4.5 厳密距離を設計費用に使う予備実験

`RESCUE_EXACT_COST=1` は、互換対ごとに逆BFSを作り、比較紙6枚が両救済紙より上にある1440開始状態からの平均最短距離を、両商品の方向で平均して設計費用にする。厳密なのはこの開始分布とcanonicalグラフに対する値であり、注文処理中の定常分布に対する期待値ではない。

練習8件10000..10007、run `20261101-055638_{imp-910,chatgpt-rescue-learned}` では、基準10.664429手に対し11.056885手、**+3.614 ± 0.653%、0/0/8**。E=0・不正出力0。

初期化終了が平均1.384倍率補正秒となり、焼きなましは平均68224反復に減った。通常版の予備比較では約987万反復だった。BFS表も平均1454個、逆辺約5.42億となる。この比較は費用指標と探索量を同時に変えており、厳密距離という指標だけが悪いと結論しない。通常版を最終64件の設定に選んだ理由は、この計算予算の問題である。

通常版の練習8件の比較は `20261101-055329_*` としてデータに含めた。少数の練習結果を最終64件に混ぜていない。

なお、`choice-check-2` の検査用基準スナップショットだけは、取得時に末尾の改行が1個多く付いたファイルであり、C++のコード内容は同一。最終比較と予備性能比較の基準は冒頭のblobとバイト単位で一致する。

```sh
python3 solutions/chatgpt-eval/generate.py --start 10000 --end 10080
python3 solutions/chatgpt-eval/self_test.py

python3 solutions/chatgpt-eval/run_compare.py --jobs 2 \
  --compare solutions/imp-910 solutions/chatgpt-rescue-layer solutions/chatgpt-rescue-learned \
  --seeds 10016-10080 --no-record -c '疎救済層: 固定設定の64件比較'

MAP_ITERS=5000 GOPT_STEPS=1500 ANNEAL_ITERS=3000000 CLIMB_ITERS=10000 \
python3 solutions/chatgpt-eval/run_compare.py --jobs 1 \
  --compare solutions/imp-910 solutions/chatgpt-multiroute \
  solutions/chatgpt-choice-potential solutions/chatgpt-edge-rewire \
  --seeds 10000-10016 --no-record -c '複数経路: 設計反復数固定の16件比較'
```

Rustが利用できる環境では `--official` で公式テスターに切り替えられる。現在のmainが測定基準から更新されている場合は、元の基準ソースを別ディレクトリへ取り出して比較する。`summarize.py` は対象runの全出力をハッシュで再検査してから集計するので、別環境で使う場合は再実行したrun-idのmanifestを用意する。

## 6. 今後1週間で優先するなら

1. **厳密距離の対象を現在の72対と少数の交換候補に絞る。** 全互換対のBFSで設計時間を使い切らず、安価な設計の後で距離を計測し局所再配置する。現在の代理費用が安い操作を選べているかを、同じ探索予算で比較する。
2. **比較器の窓割り当てと救済模様を同じ目的で設計する。** 現状は比較器だけの評価で窓を決めた後に救済紙を学習する二段階。貪欲判定を使い、比較器の辺・極性・物理窓と救済支持を共同探索する。互換辺数ではなく、重複しない72対の質と操作費用を評価する。支持数8も固定したまま最適とは主張しない。
3. **全8!グラフとの差を少数の実要求で測る。** canonical制約を外しても表示能力は増えないが、途中に非canonical配置を使うことで汎用手数が減る可能性がある。まず差を測り、大きければ短い例外経路の探索や頻出要求だけのキャッシュへ進む。旧6枚用のhelper interleaveを救済層へ対応させる効果も、汎用層の追加費用と一緒に調べる。
