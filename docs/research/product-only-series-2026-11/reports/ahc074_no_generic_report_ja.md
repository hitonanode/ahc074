# AHC074 汎用紙ゼロ構成の検証報告

## 1. 要約

**汎用紙ゼロでの表現と実行は実証できましたが、既存版を上回る手数は実現できませんでした。**

最良構成は、キャップ1枚、専用紙126枚、共有紙65枚です。全191枚の商品紙に担当目標があり、表示の補完には別の商品紙を使います。既存の6枚の汎用紙は生成しません。

公式入力100ケース（seed 0–99、計102,400注文）に対し、商品紙相互補完方式は前段の測定で平均11.485166手、誤表示0、不正操作0でした。既存版の同一入力測定は10.093223手です。汎用紙ゼロのまま表現するという仮説は支持できましたが、10手以下や首位相当の改善は未達です。

このパッケージのケース別再実行結果は `results/`、集計は `results/summary.csv` を参照してください。前段の記録と再生成後の測定は `results/previous_session_summary.json` と `results/reproduction_check.json` で区別しています。再生成による差がある場合は後者に記録します。

## 3. 最も有望な案の詳細

### 3.1 紙の構成

キャップ以外の63窓を、通常窓G=24とハンドル窓H=39に分けます。列cの紙は自分のハンドルを必ず印刷し、後の列のハンドルには穴を開けます。専用紙は担当目標に合う色、共有紙は担当する2目標が一致する場所の色を印刷します。不一致部分は穴です。

補完を担う紙も本来の担当目標を持ちます。その紙を自分の目標に使う場合も、他の目標の補完に使う場合もあります。追加穿孔は自分のハンドルを削除しません。

### 3.2 補完条件

目標uの模様をA_u、紙qの不透明マスクをO_q、黒マスクをB_qとします。主紙dを最上位に置いた後、未確定窓をRとします。紙qが次の補完紙として使える条件は、

```
((B_q XOR A_u) AND O_q AND R) == 0
```

です。すでに上の紙で確定した色は無視し、新しく見える窓だけ一致を要求します。置いた後は `R = R AND NOT O_q` と更新します。通常窓がすべて確定すれば、残るハンドルは各列の先頭の色で直せます。

補完紙は主紙と異なる列、かつ互いに異なる列から選びます。これは実行時に取り出す操作の合法性を保証しやすくするためです。

### 3.3 穴を設計する主目的

初期の紙だけでは多数の目標で補完証明が見つかりません。前段の100ケースでは平均94.26目標でした。

そこで補完候補紙について、未確定窓で目標と衝突する印刷だけを消します。ただし、自分のハンドルは消しません。候補編集ごとに256目標すべての補完証明を再計算し、未解決通常窓の総数を厳密に減らす編集だけを採用します。削った紙を主紙として使う目標も再検査するため、一方の目標だけ救って担当目標を壊す編集を抑えられます。

この設計目的は、既存の「良い補助紙に少数のハンドル穴を足す」処理より強いものです。通常窓も含めて紙の分担を調整し、商品紙だけで通常窓を埋めることを明示的に要求します。

### 3.4 表示順と取り出し順を分ける

表示順は「主紙、補完紙1、補完紙2、…」ですが、実際には選んだ紙を元の列番号の昇順に取り出します。取り出した紙は、必要な表示順になる位置へ挿入します。

先に取り出した紙は、後に取り出す列のハンドルに穴を持つため、後の列の先頭を隠しません。目的紙が列の奥なら、自分のハンドルで見えている上の紙を順にどかします。単に理想の重ね順が存在するだけでなく、それを合法な移動へ落とせることが要点です。

通常窓が完成した後に残る穴は、作業中の全紙で穴になっているハンドルです。その列は作業紙を取り出した列ではありません。必要色の紙を列先頭へ持ってくれば修復できます。必要な白・黒の紙を各列に確保することが前提です。キャップ窓の扱いは既存の1枚方式を引き継ぎます。

### 3.5 注文処理

必ず設計時の貪欲補完証明を候補に残し、幅32・深さ5のビーム探索でも別の補完列を探します。取り出し深さ、補完枚数、残るハンドルの修復費用、直前に使った紙の再利用を概算評価します。

上位5案について実際のスタックをシミュレートし、ハンドル補完紙を使う場合と直接修復する場合を比較します。表示、操作合法性、補完紙の回収可能性、384手上限を確認して採用します。既存の列の挿入位置最適化や後段の手順短縮は再利用しています。

通常窓に穴のない主紙については既存の注文処理も使いますが、汎用紙数Mは0で、表示が正しいことを確認してから採用します。

### 3.6 実装上の重要修正

キャップの番号を6から0へ変えるだけでは不十分でした。作業紙と列内紙の分類、および列0が一時的に空になるときの挿入基準も修正しています。後者を直さないと、列の紙がキャップの上に戻って列順が崩れ、注文終盤に手順生成が失敗するケースがありました。成功した最終測定は修正後です。

設計時に全191枚の担当目標数と全256目標の補完証明を監査します。通常窓の証明が得られなければ印刷前に63列へ作り直します。汎用紙への暗黙のフォールバックは行いません。

### 3.7 検証の範囲と限界

独立したC++再生器は、各移動の瞬間に紙がどこかで見えること、取り出し後の挿入位置、各注文の表示、手数上限を検査します。別のPython検査器は、注文を1つずつ渡すオンラインプロトコルで同じ規則を検査します。設計や注文処理が未来の注文を必要としないことも確認するためのものです。

公式Rust testerそのものは実行していません。また、100ケースと追加100ケースの成功は、すべての合法入力・任意長の注文列に対する成功の数学的証明ではありません。設計が失敗した場合は異常終了し、不正な出力で成功と扱うことはありません。

## 4. 捨てた案と理由

### 全窓をハンドルにする

汎用紙をなくすためのわかりやすい対照ですが、上の列ほど修復するハンドルが増えます。平均12.612666手で、表現可能性の出発点としては役立つものの、スコア上の最終案にはなりませんでした。

### 主紙＋補完紙1枚に固定する

共有する2目標の組合せを、外部の専用紙が不一致の通常窓を埋められるように選び直します。さらに補完紙の割当、列位置、ハンドル順を共同で最適化し、衝突するハンドルだけを削りました。

100ケースすべてで、専用126目標は補完0枚、共有130目標は補完1枚という構成が得られました。しかし追加ハンドル穴は平均436.67窓（344–517）と多く、平均12.100693手に悪化しました。「補完紙が少ない」ことだけを設計目的にするのは不十分です。

### 取り出しやすい列へのドナー偏重

先頭側の列の補完紙を優先する小規模実験は、seed0で11,993 / 11,930 / 11,937 / 11,912手となり、採用案を上回りませんでした。列を浅くすれば補完紙自身の穴が増えるため、取り出しだけを安くする方向には限界があります。単一ケースの実験なので、この方針全体が不可能だとは主張しません。

### 初期の不正な試作

初期実装には表示不一致や、終盤で手順生成が止まる不具合がありました。それらの数値は成功結果に含めていません。最終結果は、状態分類・列0の挿入基準を直し、独立再生器で全操作を確認した版だけを対象にしています。

## 判断

今回の結果から言えるのは「汎用紙は表現可能性の必須条件ではない」ということです。「汎用紙をなくせば手数が減る」「首位がこの構成を使っている」とは言えません。今後この方向で手数を下げるなら、補完枚数ではなく、紙の回収・取り出し・増えた穴の修復を合算した注文コストを設計時に最適化する必要があります。
