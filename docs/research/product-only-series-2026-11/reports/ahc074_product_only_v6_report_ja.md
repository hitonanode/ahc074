# AHC074 商品紙のみ v6：担当商品を固定しない背景設計

## 1. 要約

前回の v5 overlap 強化版に対し、提供入力100ケースの平均手数を **10.286123 → 10.177646手**へ削減した。差は **0.108477手／注文、11,108手、約1.0546%**。ケース別では **82勝18敗**で、全勝ではない。表示誤り・不正操作は0だった。

実装固定後に生成した別の20ケースでも、v5を今回再実行して **10.328174 → 10.213916手、0.114258手減、16勝4敗**を確認した。

中心となる変更は、背景6枚の担当商品を先に選ぶのではなく、**各紙の印刷色に一致する実在の商品が存在することを目的関数に入れ、比較窓と担当商品を共同設計する**こと。出力する紙の構造、枚数、重複担当の許容条件、注文処理は前回v5を維持している。

強化版の直列4ケース平均時間は **5.862 → 2.634秒**に短縮した。ただし、このローカル測定はAtCoder実行時間ではなく、公式2秒制限への対応は未完了である。元の6汎用紙版の保存済み参照値10.093223手には、なお **0.084424手**届かず、10.0手以下も未達。

## 3. 最も有望な案の詳細

### 3.1 v5で残っていた制約

背景紙6枚は、通常窓36個における720通りの背景を作る比較器である。各窓では2枚だけが反対色で印刷され、他の4枚は穴。15種類の紙の組をすべて使う。

v5では最初に6商品の担当を選び、その商品の色に従って、各窓で使える2枚の組を制限していた。後から担当商品を交換する近傍もあったが、印刷色が一斉に変わり、多くの比較窓を接続し直す必要がある。

この方法では、窓の割当と担当商品の良い組合せに、現在の担当を固定したまま到達しにくい。

### 3.2 担当商品を潜在変数として扱う

背景紙iの不透明窓集合をO_i、黒い窓集合をB_i、商品uのバーコードをA_uとする。

各紙について、印刷している場所で最も近い実在の商品との不一致数を

    d_i = min_u popcount((B_i XOR A_u) AND O_i)

と置く。全6枚の合計D=Σ_i d_iを、従来の共有ペア／背景移動／ハンドル差分の設計目的Fへ加える。

    objective = F + 0.1 * D

担当商品uを固定してから窓を決める代わりに、**どれかの商品と一致すればよい**という条件で窓を探索する。窓の変更に応じて、最も近い商品は変わってよい。

Dは印刷前の探索上の罰則であり、注文の表示誤りEではない。探索途中のD>0を許すことと、出力後の誤りを許すことは別である。出力する紙は担当商品と印刷が整合する形に構成され、監査される。

### 3.3 D=0なら、担当の重複衝突が起こらない理由

紙iとjは、少なくとも一つの比較窓で反対色を印刷する。したがって、同じ商品が紙iの全印刷と紙jの全印刷の両方へ一致することはない。

よって全15比較を維持する限り、D=0のとき、各紙の完全一致候補商品の集合は互いに素である。紙ごとのminを独立に計算しても、6枚の担当を別の商品として選べる。

これはD=0に到達した場合の性質であって、探索が任意の入力でD=0に達するという証明ではない。実装には、近い担当への射影・比較窓の修復と、失敗時に保存済みの有効な初期設計へ戻す経路がある。

今回の元100＋新規20バーコード集合では、強化版・軽量版とも**すべてD=0、比較窓の修復0、新設計の構築成功**だった。担当の印刷不一致を許したケースはない。

根拠：`results/design_audits.json`、各ケースの `inverse_owner_mismatches`, `inverse_repair_windows`, `inverse_initialization_ok`。

### 3.4 紙構成と重複担当の条件は前回どおり

| 役割 | 枚数 |
|---|---:|
| キャップ | 1 |
| 背景を兼務する専用商品紙 | 6 |
| 普通の専用商品紙 | 114 |
| 普通の共有商品紙 | 71 |
| 合計 | 192 |

普通の紙185枚だけで114+2×71=256商品を担当する。背景6枚にも実在の担当商品があるが、それらの6商品には普通の主紙もある。したがって、全体は**262個の担当関係が256商品を覆う重複担当構成**であり、最初の依頼の厳密な一意担当制約へ戻ったわけではない。

背景6枚は機能的には汎用的な補完を担う。担当のない汎用専用紙を増やしたわけではないが、「汎用機能そのものを廃止した」わけでもない。この留保はv5から変わらない。

キャップ以外の191枚に担当があること、専用120枚（背景6＋普通114）・共有71枚、全256商品の補完証明、階段構造を監査している。

普通の商品列は27列。背景のアクセスハンドルは物理的には設けず、全比較を持つことで一番下以外を取り出せる性質を用いる。

### 3.5 探索が速くなった理由

窓設計には、元のeswエンジンの差分評価・互換性判定・キャッシュ付き探索を再利用した。今回追加したのは、各候補状態で6枚×256商品の印刷不一致を集計する評価である。

担当が完全一致した後に、通常列の担当ペア・所属列・ハンドル順・補完価値を改善する。注文処理はv5の一枚／二枚差込み、列内再配置、合法な手順短縮を継承した。

試作では、担当確定後に旧来の固定担当窓探索を5万反復続けても、ほぼ目的値が改善しなかった。最終版はこの重い後段を省いた。探索回数を一律に増減したのではなく、探索の役割を入れ替えた。

主要な既定値：

| 設定 | 強化版 | 軽量版 |
|---|---:|---:|
| V6_MAP | 300,000 | 300,000 |
| V6_CLIMB | 60,000 | 60,000 |
| V6_OWN_PEN | 0.1 | 0.1 |
| 成功後のNG_CONTROL_MAP | 0 | 0 |
| NG_CONTROL_ANNEAL | 14,900,000 | 2,000,000 |
| PC_CLIMB | 154,000 | 30,000 |

軽量版は通常列の探索予算だけを変更し、潜在担当を使う窓設計は同じ。

### 3.6 実装中に修正した不要な制約

旧コードでは背景の担当6商品について、背景用ハンドルの0/1両色を要求していた。しかしv5以降、そのハンドルは物理窓ではなくなっており、この条件は不要である。

逆向き設計で選ばれた6商品がたまたまその窓で同色だった3ケースで、試作は旧構造へ切り替わっていた。この条件を一般的に除去した。入力番号を判定する分岐や、個別ケース用の調整はない。

最終評価では、100件・新規20件とも新設計を直接構築した。

### 3.7 検証範囲

独立C++再生器で、各操作の紙番号・挿入深さ・移動直前の可視性、操作数上限、最終表示、出力形式を検査した。

最終配布前の再検証対象は以下の364出力、372,736注文である。

| 保存出力 | 件数 |
|---|---:|
| v6強化版・元入力 | 100 |
| v6軽量版・元入力 | 100 |
| v6強化版・全商品4巡 | 100 |
| v5強化版・新規入力 | 20 |
| v6強化版・新規入力 | 20 |
| v6軽量版・新規入力 | 20 |
| 背景紙を主紙として強制する検査 | 4 |
| 合計 | 364 |

全件で誤り0・不正操作0。`results/revalidation.json` に出力SHA-256も収録した。

独立Python対話検査器では、現在の注文への操作を検証するまで次の注文を渡さない。強化版・軽量版それぞれ0000、0001、0042、0099の計8件を検査し、バッチ評価との総手数一致を確認した。

背景6枚が名目上の商品紙に過ぎないかを検査するため、0000、0047、0058、0090の全商品4巡入力で、その担当商品を背景紙の方を主紙として強制表示した。24注文×4件＝96注文すべてでこの経路が成立し、全4096注文が合法・誤り0だった。この強制検査の手数は通常の平均へ含めていない。

**公式Rust testerそのものは実行していない。** 独立C++・Python検査器による検証である。任意の合法入力・任意の注文列に対する形式的な成功証明、公式2秒制限への対応、順位表での優越を主張しない。

## 4. 捨てた案と理由

以下は基本的に元入力0000〜0007の8ケース。比較基準のv5強化版は10.340942手。

### 4.1 3商品共有

固定したv5の36通常窓背景で、3商品の共通部分を印刷した1枚と比較器だけによって全3商品を作れる組を探索した。各ケースで2商品間の互換グラフには95〜172個の三角形があったが、3商品が共通して開ける穴全体まで満たす組は**8ケースすべて0**だった。

これは固定背景・比較器のみの条件での否定結果。背景の再設計や追加の商品紙補完まで許した3商品共有を、不可能と証明したものではない。今回の方向では構築以前の候補不足が大きく、採用しなかった。

ソース：`experiments/triple_scan.cpp`、結果：`results/triple_scan8.json`。

### 4.2 各比較窓へ3枚以上印刷

全比較のアクセス性を保ちながら、2枚印刷の制約を緩めた。8ケース平均10.333862手で、改善は約0.007080手。今回求めた0.1手級には届かず不採用。

### 4.3 背景と商品紙を統合した注文処理

背景紙を従来エンジンの背景層として扱い、一枚／二枚の差込みを標準プランの回収・再利用と一緒に選ぶ版を実装した。平均10.323364手、約0.017578手の改善だった。主紙候補の扱いも変わる実験版で、最終版には採用しなかった。

### 4.4 列を決めた後で窓の役割を再割当

先に共有ペアと列を決め、その配置で実際に発生するハンドル穴を踏まえて通常窓とハンドルを交換し、再び列を改善した。平均10.311523手、改善約0.029419手。小さくは効くが、今回の主成果とはしなかった。

### 4.5 比較グラフを疎にする

すべての紙の組を比較せず、背景に許される模様の自由度を上げる案。可視性に応じた合法移動グラフを作り直して評価した。

| 比較グラフ | 比較辺数 | 平均手数 |
|---|---:|---:|
| 3つの2頂点群をまたぐ完全多部グラフ K(2,2,2) | 12 | 10.304932 |
| 完全二部グラフ K(3,3) | 9 | 10.497681 |
| 6頂点のwheel | 10 | 10.980591 |
| 完全グラフから1辺削除 | 14 | 10.334106 |

最良でも約0.036011手。背景の選択肢が増えても、紙の可視性と取り出しやすさが失われる。wheelは構築失敗後の切替を含むため、その数字を新構造だけの成績とはしない。

### 4.6 担当を完全に後付けするだけでは弱い

背景を先に最適化し、最後に近い商品を担当へ割り当て、印刷の衝突を修復する案も試した。同じ30万＋6万の探索で罰則なしの結果は10.315552手。

**最適化の順序を逆にするだけでは不十分で、担当が存在するという条件を背景探索の途中から評価する必要がある。** これが今回の最終案へつながった。

### 4.7 小規模で少し良かった追加穿孔

潜在担当案に既存のハンドル穿孔を加えると、8ケースで10.174316→10.166382手になった。追加改善は約0.007935手で、100ケースの比較は行っていない。最終版には入れず、今回の確定値には混ぜなかった。

通常窓37・38への変更も8ケースでは36窓版を上回らず不採用。

## 再現方法と注意

展開したディレクトリから、例えば：

```sh
python3 scripts/reproduce.py --method v6 --dataset original --count 100 --jobs 4
python3 scripts/reproduce.py --method fast --dataset original --count 100 --jobs 4
python3 scripts/reproduce.py --method v5 --dataset fresh --count 20 --jobs 4
python3 scripts/reproduce.py --method v6 --dataset fresh --count 20 --jobs 4
python3 scripts/verify_bundle.py
```

単体実行：

```sh
g++ -std=c++20 -O2 -march=native src/ng_product_v6.cpp -o solver
g++ -std=c++20 -O2 src/validate.cpp -o validate
./solver < inputs/0000.txt > answer.txt 2> design.log
./validate inputs/0000.txt answer.txt
```

バッチ入力には将来注文も含まれるが、ソルバは各注文の出力後に次を読む。別途、真の逐次対話で検査済み。

C++は元実装由来のx86 SIMD intrinsicを含む。対応するx86-64環境とGCC/C++20を使用する。`-march=native`、CPU、コンパイラ、環境変数の違いで実行時間や浮動小数点比較の結果が変わることがある。再現時には実験用の `V6_*`, `NG_*`, `PC_*`, `COLMDP_*`, `F3_*`, `ITER_SCALE` 等の環境変数を設定しない。

本レポートの数値は保存済み出力を基準とする。並列ベンチマークの `wall_sec` は単体性能として使わず、時間比較は `sequential_timing.json` を参照する。
