# 設計フェーズの枠組みの検討（design-frame）

2026-11-05。比較元は `solutions/esw-clean/main.cpp`。

**現行の直列処理は最適性が証明されたものではないが、今回の範囲では順序を維持するのがよい。最初の2段は独立ではない。窓割当が後段の可解な対と費用を決め、後段はその制約内でかなり配置を変える。** 同時に動かすには、焼きなましの開始時点でも共有対の修復が必要だった。cap の安い選び直し、途中の Hungarian、後段の順序逆転では得点改善を確認できなかった。

採用を勧めるのは `solutions/design-frame-lazy` の計算の省略。2000件で stdout と時間以外の stderr がすべて一致し、Hungarian の段を **29.470 → 25.067 ms（−14.9%）** にした。全体の `end_sec` の短縮は測定雑音の範囲であり、大きな時間短縮とは主張しない。

## 1. 段は独立か、どこで設計の質が決まるか

目的関数は、現在のソースでは次のように違う。説明文の古い定数には注意が必要。

| 段 | 実際に評価しているもの |
|---|---|
| 窓割当 | 近い整合対71組の貪欲費用。ハンドル差の重み **0.5**、2目標の汎用層費用、全窓の差の重み0.04 |
| `Design::initialize` | 全ての整合対を使い、ハンドル差の重み **0.65**。窓割当と完全に同じ貪欲ではない |
| 設計の焼きなまし | 列の掘り、穴の色合わせ、汎用層費用。`kHoleWeight` は **0.38** |
| filler climb | 種類・色を保つ列交換を、`cur − 0.5 × proxy` で受理 |
| Hungarian | 共有対の片側を固定した全体の目標交換を提案し、`cur − 1.0 × head value` の厳密な減少で受理 |
| 穿孔 | 最終の紙と列を使い、共通の穴埋め紙としての価値を上げる穴を選ぶ |

保存設計 `20261105-080311_esw-speed` の seed 0–199 を再実行せずに調べた。この設計は esw-clean と同一であることが既存の `20261105-084037` で確認されている。数値は [inspection-200.json](inspection-200.json)、分析器は [inspect.cpp](inspect.cpp)。

| 指標 | 200件の平均 |
|---|---:|
| 窓割当の71対と、初期化の71対の共通数 | 69.400 |
| 窓割当の71対と、最終設計の71対の共通数 | **61.735（87.0%）** |
| 初期化の71対と、最終設計の71対の共通数 | 61.335 |
| 最終対のうち、窓割当の距離26制限の外にある対 | 2.840 |
| 窓割当の目的値 | 9.859073 |
| 最終の対を、窓割当と同じ式で採点した値 | 10.008060 |
| 最終対1組のハンドル差の総数 | 8.4915 |
| そのうち、所属列より浅い側にあり、追加の穴になる差 | **3.3265（総数の39.2%）** |

87%の対が残るので第1段は強い制約を残す。一方、約9対は後段で交代し、最終対を第1段の式で測るとむしろ高くなる。後段が、列・ハンドル順・穴の偏りを使って別の対を有利にしているためである。列より深い窓は、対の色が同じでも元から穴なので、全ハンドル差を一律に数える式は最終費用そのものではない。

窓割当の解を M とすると、本来欲しい評価は「M のもとで後段まで最適化した費用」。現在の gobj はその安い近似である。後段を毎回実行することは計算量上できず、情報を返すなら、まず安い近似で有効性を確認する必要がある。

既存研究も、両方の段が重要であることを示す。

- `dsel-probe`：設計の真の標準偏差0.438%、窓割当だけの乱数変更0.418%、同じ割当で焼きなましだけ変更0.344%、最後の再割当・穿孔だけ0.050%。これは別々の介入なので、分散を足して「第1段が何%を説明する」とは言えない。根拠は trial_log の2026-11-05、`20261104-225055`、`225204–230448`、`230947`以降、`231739`以降、`233442`以降。
- `20261105-064212`、2000件：窓割当2倍は **−0.154 ± 0.026%**、焼きなまし2倍は **−0.075 ± 0.022%**。gobj の低下0.052と得点の改善が対応し、gobj 1あたり約3%という関係には介入の裏付けがある。
- `pair-exact`、`20261105-101118`：貪欲と厳密な最小費用マッチングの差は0.0017。後段の初期化を厳密にしても `101241`、200件で +0.026 ± 0.071%。したがって、単に貪欲を正確にする余地は小さい。

## 2. 同時最適化・交互最適化

### 対を壊さない局所変更の全列挙

「焼きなましの早い時点なら窓を動かしやすいか」を、同じ保存設計の seed 0–31 で調べた。割当後の実際の `Design::initialize` の状態と最終状態について、既存の対を固定して次を全列挙した。解析であり、注文列を使った評価ではない。

| 単一窓の変更 | 候補数/件 | 壊れる対：初期化直後 | 壊れる対：最終 |
|---|---:|---:|---:|
| 汎用窓の極性反転 | 38 | 17.536 | 17.573 |
| 汎用窓のシート対と極性の変更 | 平均952 | 9.116 | 9.106 |
| 汎用窓とハンドル窓の交換、2極性 | 1900 | 8.288 | 8.581 |

シート対変更は15種類の比較辺が全部残るものに限定した。過去の「約30対を壊す」は今回の単一窓近傍にはそのまま当てはまらず、**平均8–18対**だった。しかし、初期化直後でも最終状態とほぼ同じである。

壊れる対が0の候補では、所属列のハンドル色の一致、各列の両色の存在も確認し、既存の列と対を固定した `Design` のモデル費用を計算した。許される候補は初期化直後 **3.406/件**、最終 **2.344/件**。**モデル費用を下げた候補はどちらも0**だった。

根拠：[joint-32.json](joint-32.json)。初期化直後と最終を調べた結果であり、焼きなまし中の高温状態すべてや、複数窓を同時に変える手を否定するものではない。改善には窓の変更だけでなく、対の再編成・列の修復まで含む大きな手が必要になる。単純な小変更を既存の高速な焼きなましに足す方向には、今回の標本で利得がなかった。

### Hungarian を焼きなましの間へ移す

`design-frame-midmatch`：4区間の第2区間の後に Hungarian を2回、最後に2回実行する。合計4回、焼きなましの候補数と温度区間は維持。全体の交換の後、残りの焼きなましで列やハンドル順を適応させる狙い。

200件で **+0.054 ± 0.052%**、91勝2分107敗。改善を確認できず、採用しない。既存の head-steer は途中でフィラー価値を上げても後の filler climb が追いつくという結果だったが、今回は異なる全体の再割当でも利得が出なかった。

## 3. cap の位置と多様性

窓の番号は入力分布上対称であり、63番そのものが有利なのではない。ただし、cap を変えるとよいというためには、増える多様性から有利な設計を安く選べる必要がある。

`design-frame-cap` では窓割当の直後、**列が存在する前**に、汎用窓以外の26窓のどれを cap にするか選ぶ。比較器は固定されるので、共有対の整合性を壊さず、列の修復もいらない。この点が、既存設計の cap を交換する試みとの違い。71対の元の貪欲費用で選び、その後を通常どおり実行した。

- 200件中56件（28%）で cap が変わる。残り144件は出力も同じ。
- gobj の改善は **−0.007043 ± 0.001134**。71対の共通数は70.21で、選ぶ対も大半は同じ。
- 選択の追加時間は平均 **0.810 ms**。既存の gobj と得点の傾きを機械的に当てても期待値は約−0.021%で、小さい。cap への介入に同じ傾きが成り立つと確認したわけではない。
- 通常比較200件で **+0.002 ± 0.041%**、27勝144分29敗。改善を確認できず、採用しない。

根拠は `20261105-115055_design-frame-cap`。これは26個の完全な設計を作って選ぶ実験ではない。残りの汎用窓も含めた複数設計や、もっと良い早期予測器の効果は未検証。以前の capjoint / capswap や割当の多スタートが勝たなかった事実と合わせ、位置の多様性だけを目的に計算量を使う根拠はまだない。

## 4. 後段を織り込む窓割当の目的関数

`design-frame-ordercost` は、71対のハンドル差が少数の窓に集中すれば、その窓を深い側へ置いて差を穴に隠せることを見積もる。割当の提案・足切りの仕組みは変更しない。

ハンドルごとの違う対の数を昇順に f_j（j=0,…,H−1）とし、次を gobj に足した。

```
0.5 / 71 × { Σ f_j (H − j) / (H + 1) − 0.5 Σ f_j }
```

線形の列深さ分布を仮定し、平均の重みは従来の0.5とそろえる。全窓で差の数が同じなら補正は0。係数0.5で、後段の色の制約・列ごとの組成を無視する見積りを弱めた。前節の39.2%という観測が、このような後段の情報を試す理由である。以前の as6-gproxy（色の偏り・差の分散を追加）も最終的な利得がほぼ消えており、この補正も実得点で判断する。

| 版 | 窓割当の反復数 | 件数 | 得点差 ± SE | 勝/分/敗 |
|---|---:|---:|---:|---:|
| ordercost | 100% | 24 | −0.183 ± 0.248% | 13/0/11 |
| orderfast | 76% | 200 | −0.008 ± 0.080% | 99/2/99 |
| orderfast | 76% | 500 | **+0.018 ± 0.051%** | 241/2/257 |
| balanced | 82% | 200 | **+0.020 ± 0.082%** | 91/0/109 |

100%の試走は `20261105-120859`。map_end_sec が0.486 → 0.641秒と増え、実時間2秒超えが2件（seed 7、17）あったため、この予算のままの評価は延長しなかった。

76%版は `20261105-121040`。500件では map_end_sec 0.4712 → 0.4376秒、helper_end_sec 1.0883 → 1.0534秒、end_sec 1.4694 → 1.4363秒。モデル費用は8.23768 → 8.23590だが、得点改善は確認できない。

500件の時間比から、ほぼ同時間になるよう余った予算を戻した82%版は `20261105-121534`。200件で map_end_sec 0.4653 → 0.4765秒、helper_end_sec 1.0733 → 1.0823秒（差+0.0090 ± 0.0062秒）、end_sec 1.4510 → 1.4605秒。モデル費用は8.23781 → 8.22792（差−0.00989 ± 0.00329）だが、得点では改善を確認できなかった。両方ともWA・実時間2秒超え0件。**この近似を同時間の改善として採用する根拠は得られなかった。** 200件の誤差は大きく、あらゆる後段の評価式が無効だという結論ではない。

## 5. 後段の順序と、出力を変えない高速化

### Hungarian → filler climb への順序逆転

`design-frame-postclimb` は全ての回数・重みを維持し、Hungarian の後でフィラーの列交換を行う。200件で **+0.139 ± 0.036%**、81勝1分118敗となり、悪化した。

最終 model_cost は8.23781 → 8.22155と下がっている。したがって、モデルを下げるよう段を並べ替えるだけでは得点の改善を保証できない。`proxy_after` は0.54169 → 0.58042だが、基準は Hungarian 前、逆転版は後の値なので、これを最終設計同士の J の比較として扱ってはいけない。自然な設計のばらつきを予測する代理値と、その代理値を直接改善する操作の因果効果は別である。

穿孔は、最終的な紙の模様と列を入力にする。これを前へ動かすなら、以後の対・列の交換が追加の穴をどう継承するかをモデルに入れ直す必要がある。今回はそこまでの変更はしていない。前へ動かす効果は未確認であり、最後に行う現行の配置を維持する。

### design-frame-lazy：同じ計算結果で、使わない評価を省く

変更は2点だけ。

1. `ProbabilityHead` のコンストラクタが行った `rebuild()` の戻り値を保存する。直後に同じ状態で呼んでいた2回目の全再計算を除く。
2. 単独紙への割当利益 `single_target[target][column]` を、色と整合性の検査を通り、Hungarian の行列で使うときだけ計算する。状態が固定された1回の行列構築の中で再利用する。

`target()` は状態を変えず、値は非負。未計算を−1として区別できる。値の演算順、乱数の消費、採否は変わらない。AF_PROFILE の呼出回数は実際に省いた分だけ減るが、計測機能そのものは残している。

`20261105-115055_esw-clean` / `20261105-115055_design-frame-lazy`、seed 0–1999：

| 指標 | esw-clean | lazy | 対応する seed 間の差 ± SE |
|---|---:|---:|---:|
| 平均スコア | 10344.19 | 10344.19 | 0.000 ± 0.000% |
| match_sec | 0.029470 | 0.025067 | **−0.004404 ± 0.000071秒** |
| helper_end_sec | 1.073531 | 1.072108 | −0.001424 ± 0.001328秒 |
| end_sec | 1.443009 | 1.442710 | −0.000300 ± 0.001530秒 |

2000件全てで **stdout 完全一致、時間以外の stderr 完全一致**。WA 0、勝/分/敗 0/2000/0。確認結果は [lazy-summary-2000.json](lazy-summary-2000.json)。

評価はGCC C++23で実施。採用候補はClang C++23 `-O2 -Wall -Wextra` でも、通常ビルドと `-DLOCAL_BENCH -DCLOCK_SCALE=1.1` の両方が警告0でビルドできた。現在のlazyのソースが2000件の評価時の保存ソースと同一であることも確認した。実験スイッチ全組合せを再評価したという意味ではない。

時間の裾も改善したとは言えない。実時間p99は1.474 → 1.516秒、最大1.827 → 1.969秒で、両方とも実時間2秒超え0件。end_secの1.8/1.9/2.0秒超えは基準1/1/0件、lazy 2/2/1件。得点・探索量が同じでも、段ごとの時間には実行環境のばらつきがある。今回の確かな計測上の利得は Hungarian 内の4.4 msである。ユーザー提示のジャッジ時間模型（平均1.60秒、p99 1.76秒）を、この4.4 msだけで大きく変えるものではない。

## 6. 通常比較の一覧と時間

いずれも `scripts/pahcer_run.py --compare` と `--extend` で記録した。負の得点差が改善、±はケースごとの log スコア比の平均の標準誤差。固定設計の評価を設計変更の比較には使っていない。

共通 run 接頭辞 `20261105-115055`、seed 0–199：

| 解法の末尾 | 差 ± SE | 勝/分/敗 | helper_end_sec | end_sec | 判断 |
|---|---:|---:|---:|---:|---|
| esw-clean | 基準 | — | 1.08045 | 1.44585 | 基準 |
| design-frame-cap | +0.002 ± 0.041% | 27/144/29 | 1.07266 | 1.43522 | 改善未確認 |

基準とlazyは同じ run-id のまま2000件へ延長したため、上表はその最初の200件だけの値。時間は全て CLOCK_SCALE 込み。段の回数が同じでも、数msの全体時間の差をそのまま変更の効果とは解釈しない。

121534の200件は評価外負荷0.12・0.26コア。スコア比較の追加評価は、採用できる候補がなくなった時点で止めた。lazyは得点差の検出ではなく同一性と時間の確認のため、2000件まで調べた。

## 7. 推奨と再現方法

- **現行の段の順序を維持し、lazyの2点だけを移植する。** 共有対を壊す同時最適化、単純な再始動、代理値だけによる順序変更を採用する根拠は得られなかった。
- 窓割当の gobj を同じ時間で下げる探索の研究は引き続き有望。これは別セッションの担当であり、今回その内部探索は変更していない。
- 今後、段を結び付けるなら、対を修復した後の費用まで含む少数の大きな候補を、現在の高速な探索に勝る時間で評価できるかが課題。今回はそこまでの候補を実装しておらず、同時最適化全般が不可能という結論ではない。
- 設計選択には、最終 J の相関だけでなく、短い探索の時点の順位が十分残ることと、候補を増やす損を上回ることの両方が必要。現時点のcap選択にはその証拠がない。

各実装は `design-frame-*` の日本語READMEに記載。[build_variants.py](build_variants.py) は esw-clean から差分を再生成する。既存のCLOCK_SCALE、LOCAL_BENCH、DesignStore、全ログ・スイッチ・プロファイラ・目次と段の目印・`@paper`/`@ops`を維持した。共有ファイル・他の解法・trial_log.mdは編集せず、コミットしていない。

解析の再現例（リポジトリのルートから）：

```sh
flock -s /home/sato/ahc074/runs/.lock g++ -std=c++23 -O2 -DCLOCK_SCALE=1.1 -DLOCAL_BENCH solutions/design-frame/inspect.cpp -o solutions/design-frame/inspect
python3 solutions/design-frame/run_inspection.py --seeds 0-200 --output inspection-200.json
python3 solutions/design-frame/run_inspection.py --seeds 0-32 --moves --output joint-32.json
python3 solutions/design-frame/summarize.py 20261105-115055_esw-clean 20261105-115055_design-frame-lazy --seeds 0-2000 --identity --output lazy-summary-2000.json
```

解析器は公開のバーコードと保存設計だけを読む。解法やテスターを直接実行しない。解析・コンパイルも評価の共有ロックで排他する。`bin/g++` は、評価スクリプトのロック取得より前に行われるコンパイルも評価に重ならないようにするラッパーで、新しい比較はこれをPATHの先頭へ加えて実行した。
