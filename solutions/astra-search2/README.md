# astra-search2

改良元: solutions/astra-search

`assign_windows` の停滞時の進み方を変える。元の手の種類、選択済み70対を4対以上壊す候補の事前除外、厳密な目的関数、候補の評価キャッシュは維持する。

- 現在の状態で厳密評価した候補のうち、受理を検討できる最小費用の候補を保存する。
- 焼きなましでは2048候補以上、最後の探索区間では4096候補以上受理がなければ、保存した候補へ直接進む。少し費用が上がる場合も進むことで、同じキャッシュ済み候補を繰り返す停滞を解く。通常時の焼きなまし温度は元のまま。
- 変更を受理したら、その変更を戻す逆手を4受理分避ける。ただし、厳密評価で探索全体の最良値を更新する逆手にはこの制限を適用しない。
- 受理ごとに保存候補を無効化する。直接進む候補の費用は同じ状態のキャッシュ値を使い、受理時に全対の制約とマッチングを再構築する。
- 最後の0.11秒でも停滞時の移動を続け、その区間で訪れた最良状態を返す。途中で費用が上がった状態のまま終了しない。

目的関数 matching_cost、距離上限26、kMapEnd=0.50 / kGoptEnd=0.61、他の段は変更しない。時計は従来どおり CLOCK_SCALE 倍する。

追加のstderr指標:

- `forced_steps`: 焼きなまし中、停滞対策で費用が上がる候補へ進んだ回数。
- `climb_forced_steps`: 最後の探索区間で同様に進んだ回数。
- `tabu_skips`: 直近の逆手として受理を避けた候補数。
- `direct_steps`: 保存した最小費用候補を直接取り出した回数。

既存の `search_exact_evals` は新しく全対を評価した回数であり、受理時の再構築は含まない。`search_memo_hits` は保存候補へ直接進む際の再利用も含む。`map_iters` / `gopt_steps` は除外を含む試行回数なので、これだけで探索の速さを判断しない。

計測方法、評価結果、不採用案は [REPORT.md](REPORT.md) に記録する。
