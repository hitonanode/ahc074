# 私有窓を持つ汎用紙の検証

## 結論

独立した生成500件では、現行最強 `astra-search4` に対して **+0.8197 ± 0.0895%** 悪化した。平均手数は **10.666635 → 10.754547手/注文**。現版は採用しない。

全500件で合法な出力と正しい表示を確認し、新しい可視性の仕組みは動作した。一方、私有窓で制約される商品対の選択と、70対未満の候補を改善できない学習器に具体的な課題が残った。今回の結果はこの実装と探索の評価であり、私有窓を使う構造全体の不可能性を示したものではない。

## 何を変えたか

6枚の汎用紙のうち紙0に私有窓を一つ与え、専用紙を戻して汎用層を露出させれば、紙0が汎用紙の最下位でも取り出せるようにした。他の5枚には全10組の比較窓を残す。保護窓は計11個となり、36汎用窓のうち25窓を学習に使える。

私有窓の最終表示は専用紙Dが印刷する。対にする二商品がその窓で一致することを条件にし、全てのDを私有窓で不透明にする。このため、私有窓のランダムな要求色を毎注文汎用紙で直す操作は不要である。紙の追加もない。代償は、私有窓で色の違う商品対を使えなくなることである。

## 新しい可視性は実際に使われたか

16件の出力を調べ、全てで次を確認した。

- 私有窓は、汎用紙0だけが白、他の5枚の汎用紙は穴。
- 186枚の専用紙は全て私有窓で不透明。
- 汎用紙0が6枚の汎用紙の最下位にいる状態から動かす操作が、合計866回、平均54.125回/ケースあった。最小33回、最大67回。

従来の全2枚比較器では、最下位の汎用紙は他の汎用紙に必ず隠れる。従って、この866回は新しい私有窓の可視性を利用した操作である。その操作回数自体が節約手数を表すわけではない。別の操作順を使った場合との差は、最終スコアで比較する必要がある。

16件全てでG=36、初期設計は1回で成功した。再試行・失敗・不正な計画・誤表示はいずれも0。ゲート学習後に3枚以上を使う窓が残ったのは5件で、残る11件では私有窓以外は2枚比較器だった。私有窓そのものは全件で維持している。

## 私有窓で失う対と、学習器に残る問題

私有窓の制約により、設置前の70対のうち平均18対が使えなくなった。設置前に互換だった距離26以下の対は平均197.31組で、選んだ私有窓で色が一致するものは平均139.38組だった。

私有窓の選定時に貪欲法で取れた対は平均68.25対、最小64対、最大70対。この不足は、そのまま「本実装が全商品を表示できない」という意味ではない。最終的な `Design.initialize` は全ての商品対を調べ、長さ3の増加道も使う。こちらは16件全てで70対を作ることに成功した。

### 代理費用の大きな値は実費用ではない

学習器の `exact_score` は、近い対の貪欲マッチングが70対に達しない場合に `1e9` を返す。stderrでは256で割るため、`decoder_proxy_before` または `decoder_proxy_after` が **3906250** になる。

これは未成立を示すsentinelであり、実際に必要な手数でも費用の見積もりでもない。**この値を含む平均を、設計費用として解釈してはいけない。**

|段階|70対の値がある件数|sentinelの件数|
|---|---:|---:|
|ゲート学習前|6/16|10/16|
|ゲート学習後|12/16|4/16|

有効な値だけの平均も、学習前後で対象ケースが違うため単純比較しない。ケース番号と件数は `pilot_mechanism.json` に保存した。

### 貪欲法の偽陰性と、距離上限による不足を分けた

学習後もsentinelだった4ケースについて、出力された6枚の汎用紙の実際の模様から、距離26以下の互換対グラフを再構築した。720順列を全て調べて対の両側の表示可能性を判定し、そのグラフの最大基数マッチングを厳密に求めた。

|生成seed|近い互換対の辺数|厳密な最大マッチング|判断|
|---|---:|---:|---|
|149|142|71対|70対は存在する。貪欲法の偽陰性|
|150|124|68対|距離26以下だけでは70対を作れない|
|152|129|66対|距離26以下だけでは70対を作れない|
|158|149|70対|70対は存在する。貪欲法の偽陰性|

診断は `matching_probe.py`、結果は `matching_diagnostic.json` に保存した。最大マッチングの実装は、2〜10頂点の270個の小さいグラフについて独立な部分集合全探索と一致することを確認した。

この切り分けから、次に変えるべき部分が具体的になる。

1. 学習器にも増加道を入れ、貪欲法だけで70対が存在しないと判定しない。
2. 70対未満の候補を全て捨てず、まず不足数を減らす目的を使う。現実装は一窓の変更で一気に70対になる候補しか採用できず、64→66→68→70のような段階的改善を進められない。
3. 私有窓の制約がある場合、距離26という候補上限を再検討する。少なくともseed150と152は、現時点の印刷を固定したまま貪欲法を厳密化するだけでは解消しない。

これらは次に調べる具体的な候補であり、修正後のスコア改善を実証したものではない。500件の比較に使ったソースは変更していない。

## 正しさの構造検査

`verify.cpp` は診断用の固定した合法印刷を作り、安全な操作グラフと、実際の模様から作る操作グラフを別々に調べる。

- 全36600遷移の取り出し元が実際に可視であることと、遷移先が直接の取り出し・挿入で作った順序と一致することを検査。
- その中の1200遷移が、最下位の私有紙0を動かす操作であることを検査。
- 両方の720状態グラフで全点対距離が有限、直径5であることを検査。
- 1200個の目標集合について、距離球のOR/popcountによる平均距離が、全720始状態からの直接の最短距離の平均と一致。

不一致は0だった。これは提出形式の全ケース評価を代替するものではない。実際の学習済み印刷の正しさは、16件の動作確認と独立500件の対話評価、それぞれの全操作の独立再生でも検査した。

提出用 `main.cpp` のSHA-256は `a872e1993c32f559e79a58c566dae3cad23a586c5083ce98a03e8496ca281276`。構造検査のソースhash・コンパイラ・出力は `verification.json` と `verification.txt` に保存した。

## 再現

共通の手順で生成入力を置いた評価用workspaceを作り、次を実行する。

```sh
python3 solutions/astra-frontier/evaluate.py \
  --compare solutions/astra-search4 solutions/astra-privategate \
  --seeds 144-160 --no-record -c 'private generic window pilot'

python3 solutions/astra-frontier/evaluate.py \
  --compare solutions/astra-search4 solutions/astra-earlytable solutions/astra-privategate \
  --seeds 1000-1500 --no-record -c 'private generic window holdout'

g++ -std=c++23 -O2 -DCLOCK_SCALE=1.1 \
  solutions/astra-privategate/verify.cpp -o /tmp/verify-privategate
/tmp/verify-privategate

python3 solutions/astra-privategate/matching_probe.py \
  runs/20261101-195719_astra-privategate \
  --seeds 149,150,152,158
```

最後のコマンドのrun-idは、再実行してできたrunへ置き換える。入力seedと保存出力を一致させる必要がある。
