# 背景ヘルパー計画の共通化と設計時間への再配分

## 実装前のモデル

`nogen-helper-model` の保存設計50件×注文2列（run `20261106-095954`）で、背景ヘルパー0.2914秒のうち0.2435秒が独立した後処理だった。後処理後の勝者の93.2%は未加工評価でも上位3に入った。この測定を根拠に、まず注文の計画・後処理を統合した。

`nogen-joint-model` の保存設計32件（run `20261106-095422`）では、背景窓を固定した後のキャップ再選択は0.00835±0.00331手/注文、既存穿孔は0.00668±0.00079手/注文のモデル利得しかなかった。いずれも0.52手の差に対して小さく、この局所変更の本実装は後回しにした。大きな設計変更の可能性全般を否定する結果ではない。

## 採用した変更

1. `process_ng` が通常計画の完了後にヘルパーを別々に後処理する構成を廃止。`try_product_helpers` は未加工計画を生成し、`process` の通常・拡張候補集合へ渡す。共通の後処理、排出、中立変更、同一要求の文脈と計画キャッシュを使う。
2. 時間短縮を使い、ペアヘルパーの候補深さ2→3、予備候補6→16、実計画2→4、単独ヘルパー2→3へ拡張。紙の色は変更しない。
3. 背景窓目的関数の整数費用の辺整列を安定radix sortへ置換。比較ソートの（費用、ペア番号）の順序を保つ。
4. 背景窓探索を6000→9000反復へ拡張。列設計などは同じ。探索の時計停止と1.70秒からの軽量注文処理を維持。

これは承認された書き換えのうち、背景ヘルパーの共通計画・後処理への統合と時間再配分の段階。キャップ・背景・列を一体で最適化する設計器はまだ実装していない。

### TLE安全策と検証

- LOCAL_BENCHは軽量処理を無効にしているため、模型2秒超が1件残る。seed **813**、helper_end 1.14109、req 0.603911、end 1.76364、judge模型2.020652。評価上の実時間2秒超は0件。
- 提出版は scaled clock の1.70秒から軽量処理へ入り、設計窓探索は1.00秒、列探索は1.15秒を上限にする。時計の読みは既存の scaled_since を維持。模型の最大値を、ガードを有効にした提出実行の実測と混同しない。
- `20261106-101525_nogen-map9k-lightcheck`、保存した最終設計50件×注文2列、全1024注文で軽量処理を強制。全100実行でWA 0、E 0、所有色違反0。req_secは平均0.028285秒、最大0.033447秒。
- g++ / clang++、LOCAL_BENCHあり・なしの4構成を C++23 -O2 -Wall -Wextra -Werror でビルド成功。手動ビルドは共有flockで保護し、/tmpの実行ファイルは削除。
- 最終2000件で64窓の所有色違反0、無所有商品紙0、E 0、操作ラベル不整合0。全191非cap紙に実商品の所有者がある。
- radix sortのみの50件比較はstdoutも50/50一致。

### 残る問題と次の設計

SOTAとの差は **0.481772操作/注文**。主なラベル差（map9k − SOTA）は fix +0.387575、repair +0.239491、fret +0.126827、help +0.096103、hdig +0.066229、dig −0.249813、lift −0.076884、fill −0.108865。ラベルは生成場所を示すため、repair増をそのまま構造の悪化とは解釈しない。共通後処理でfixがrepairに書き換わる分も含む。

列費用は2.696859、ハンドル費用4.571666、背景費用1.411087。旧版のハンドル4.590360からの改善は限定的であり、今後は背景窓の代理費用と実際のペア・列・ハンドル費用をそろえる統合設計が本題になる。

追加モデル `nogen-cap-model`（run 20261106-101259、旧保存設計32件）は、キャップを全穴にし、異色ペアのキャップ穴を背景商品の実色で補う案を測定した。互換辺は平均330.375から453.406へ増え、模型利得0.025318±0.007562手/注文。背景窓固定での値なので、次はwarm startと背景窓の同時調整を測り、実費用を使う統合設計の入口として検討する。汎用紙や自由な比較用の色は導入しない。
