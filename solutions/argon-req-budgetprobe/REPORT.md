# R5: 注文の特徴に応じた探索予算

## 指摘と現在のコード

助言01-4は「仮決定した操作手数が多い……クエリ」に追加計画・中立探索・3削除・内部アンカー・最良解の再編集を集中させると提案する。

`argon-des-perf-latew105` の `SearchConfig` と `Request processing (process)` は固定の予算を使うので、注文ごとの配分という指摘は現在も有効。一方、中立探索は既に2周であり、助言の1周という前提は古い。また基準には残時間による打ち切りを意図的に設けておらず、余剰時間が大きいわけではない。今回は時計を探索判断に使わず、探索前に分かる特徴で決定する。

## 同一開始状態の測定

`budgetprobe` は実際の注文を基準で解いた後、同じ積層から次の予算で解き直す。採用状態は必ず基準へ戻す。未来の注文は読まない。

| 番号 | 予算 |
|---|---|
| 0 | 中立候補の再編集を削除だけに限定 |
| 1 | 0に加えて中立探索を1周へ縮小 |
| 2 | 中立4周、追加候補8、追加計画上限2、短い計画への限定を解除、3削除、内部深さ4、最良計画の再編集1回 |

説明変数は初期手数、通常の編集・eject後の手数、製品紙の穴数、列深さ、旧フィラー数、初期候補間の値差。第1中立周回の改善も診断用に記録するが、それ以前に予算を選ぶ規則には使用しない。応答は完成後のplan_costと実測時間。測定版の反復によるキャッシュ・分岐予測の影響があるため、時間は配分案を作る目安とし、採否は通常の同時比較で判定する。

学習用seed 0–99と検証用100–199を分ける。状態価値の差は実現スコアそのものではないので、配分案は別途オンライン実行で比較する。

## 最初の測定結果

`20261106-074004_argon-des-perf-latew105` / `20261106-074004_argon-req-budgetprobe`、200×2。400 stdoutと全@paper/@opsが一致、0/200/0、全予算の内部検査失敗0。外部負荷平均0.15・最大0.34コア。先行する8×2 (`20261106-073507_*`) では第1周回の指標が常に0となる計測条件を発見し、周回番号1の判定へ修正してから200×2を新規実行した。探索・出力に影響する修正ではない。

| 予算 | 注文ごとの完成評価差の合計/ケース（正が改善） | 再実行のreq秒 |
|---|---:|---:|
| 実際の基準 | 0 | 0.456452 |
| 削除だけの再編集 | −5.73707 | 0.353118 |
| さらに1周へ縮小 | −8.88041 | 0.317594 |
| 重量設定 | +7.44593 | 0.624962 |

通常eject後の長さが5–7手の注文では重量化の平均利得0.00296/注文、追加34µs。15手以上では0.01394/注文だが追加561µsで、長い注文へ単純に集中する方が効率は低かった。これは実現スコアの差ではない。seed 0–99で深さ3の予算選択木を作り100–199で検査しても、時間内で0.03%相当を得る配分は見つからなかった。得られた選択木は実装せず、重い設定を機能ごとに分解した。

中立探索には既に「改善がなければ次の周回へ行かない」停止条件があるため、最大周回数が固定でも全注文で同じ仕事をしているわけではない。内部アンカーの残余利得は約0.0007%相当なので対象外とした。

## 初版と費用の診断

`argon-req-budget-adapt` は継続利得0.05、追加計画4・短い計画への限定解除、通常eject後11手以下で3削除という配分。既存F3_*を明示すればその値を優先する。

`20261106-075637_*`、24×2→200×2は **−0.028283±0.003854%**、132/0/68。req **0.443690→0.503735秒**（+13.53%）。ジャッジ平均 **1.590289→1.672139**、p99 1.754726→1.821193、最大1.805567→1.897407、2秒超え0→0。全件WA / self_wrong / op_label_errors = 0、延長時外部負荷平均0.18・最大0.29コア。利得は明確だが、約0.346%/追加ジャッジ秒で費用条件と空き予算を満たさない。

`20261106-075852_argon-req-budget-base-profile` / `_argon-req-budget-adapt-profile`、24×2でCOLFAST_PROFILE / F3_PROFILE / PLAN_TRACE / HEAVY_PREDICTを有効化。両腕とも対応する非計測版の48 stdoutと全@paper/@opsに一致。追加計画の段は0.000003→0.079722秒/ケース、中立候補の再編集は0.089837→0.081027秒。再編集の節約だけでは追加計画の費用を賄えない。

#f2planの326.02試行/ケースのうち、安い削除後に値差1.0以内なのは108.02試行。そこでの局所評価改善は全試行5.37104のうち2.69963、段の時間は0.07953のうち0.01901秒だった。値差を広げるほど利得は増えるが費用も急増するため、この条件を改修に使う。

observe.pyのcases / queries / state / statsも確認した（`../argon-req-budget-adapt/episodes.log`）。seed 197は−24手、r624で分岐した後r752で積層が再合流する区間が−18手。seed 49は+21手、r129からr820の再合流区間が+28手。後続の選択も区間差に含まれるため、最初の1選択だけの因果効果とはみなさない。局所評価差と実現手数を分けて判断した。

## 原因に対応した改修と結論

`argon-req-budget-gap1` は追加計画を安い削除で整えた後、通常eject後の基準値から1.0以内の場合だけ本格編集・ejectを実行する。単純なraw値で早期に捨てるのではなく、削除による回復を見てから予算を配る。既存F3_PLAN_GAPが明示された場合は従来の指定を優先する。上の5.37104等は中立探索前の一時的な利得であり、最終スコア改善と同じではない。

基準・初版・改修を同時に測った `20261106-080224_*`、24×2→200×2:

| 解法 | 平均log比 ± SE (%) | 勝/分/敗 | req_sec | ジャッジ平均 | p99 | 最大 | 2秒超え |
|---|---:|---:|---:|---:|---:|---:|---:|
| argon-des-perf-latew105 | 0 | 0/200/0 | 0.441594 | 1.587789 | 1.727925 | 1.821261 | 0/400 |
| budget-adapt | −0.028283 ± 0.003854 | 132/0/68 | 0.502377 | 1.670311 | 1.824432 | 1.908128 | 0/400 |
| budget-gap1 | **−0.016424 ± 0.003234** | **123/0/77** | **0.458385** | **1.610863** | **1.756475** | **1.819883** | **0/400** |

全件WA / self_wrong / op_label_errors = 0、外部負荷平均0.16・最大0.34コア。req比は初版1.13765、改修1.03802。改修はジャッジ平均増分を+0.082522→**+0.023075秒**まで減らしたが、利得も減った。約0.712%/追加ジャッジ秒という費用率は満たす一方、空き予算+0.015秒を超え、採用閾値0.03%にも達しない。焼きなまし削減で不足時間を支払っても利得がさらに減るため、結合候補は作らない。

**R5は不採用として終了する。** 固定予算の配分には改善余地があり、今回も統計的な利得は確認した。しかし、低費用の既存処理を削る損失と追加候補の仕上げ費用を両方入れると、現在の時間・実用利得の条件を満たさなかった。BASE.mdの新方針（失敗案は初版＋原因に対応した改修1回、各延長段で確かな改善、採用0.03%以上）に従う。固定2000×2と通常2000件の採用確認へは進めていない。一般的な適応予算すべての不可能性を示したものではない。

既存機能・ログ・スイッチを残し、目的関数・設計・CLOCK_SCALE・DesignStore・節・目次を変更していない。新しい節は追加していない。詳細な集計は各測定ディレクトリのanalysis.log / results.json / metrics.json、再現用スクリプトに保存した。通常runは今回追加しておらず、固定設計runは仕様通りpahcer非登録。

## 検証と再現用記録

改修版の実測追加計画処理は321.505→105.770回/ケース、値差による省略215.575回。中立周回は基準1396.315→1262.988回/ケースだった。安い処理による条件判定自体は残るため、全追加時間が消えるわけではない。
