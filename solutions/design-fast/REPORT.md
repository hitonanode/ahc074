# design-fast: 窓の割り当てを出力を変えずに速くした記録

改良元は solutions/climb4-fast です。手を入れたのは窓の割り当て（assign_windows と、そこから呼ぶ PosetSums・WindowRelations・WindowPairs・evaluate_move・スクリーン・matching_cost）だけで、climb4-fast の 734〜1835 行の範囲です（作業した agent の報告から保存）。

## 結果

| run | seed | map_end_sec | helper_end_sec | stdout |
|---|---|---|---|---|
| 20261105-075858（最終版） | 0〜999 | 0.6755 → 0.4628（0.685） | 1.4072 → 1.1959（0.850） | 1000 件同じ |
| 20261105-075613（同じソース） | 0〜199 | 0.7070 → 0.4870（0.689） | 1.4443 → 1.2230（0.847） | 200 件同じ |

- 比は同じ run の平均どうしの比です。
- 時間以外の stderr 指標も全件同じでした。
- -march=native（GCC・Clang）の設計の出力が同じで、POSET_VERIFY は 130023 個すべて一致しました。

## 計測の方法

- DESIGN_PROFILE の rdtsc サイクルを使いました。数字は 1 seed あたりの百万サイクルで、TSC は約 3.65 GHz です。
- プロファイルは pahcer_run.py で 48 seed・24 並列に回して取りました。前後は同じ run 20261105-080313 で比べています（climb4-fast に計測だけを入れたものと最終版。両者の出力は 48 件同じ）。
- 途中の試行は、評価が走っていないときだけ、1 コアに固定して seed 0〜2 の設計だけの入力で比べました。単発の計測は ±3% ほどぶれます。

## 変更と効果

1. **PosetSums を正準な鍵の表にした。** 関係とその転置は同じ値を持つので、30 ビットに詰めた形の小さい方を鍵にしました。鍵は 65012 個です。
   - 引き方は変位ハッシュ（CHD）です。表は 32 KB + 256 KB で、鍵の比較も探索の繰り返しもありません。
   - 表を引く段は 162 → 79 になりました（seed 0）。
2. **2 MB の関係キャッシュをやめ、閉路の判定は閉包だけにした。** スクリーンは cyclic(r) だけを見ます。
   - 1 と 3 を入れた最初の版（run 20261105-070613、48 seed）で、map 0.736 → 0.709。
   - スクリーンは 196 → 89 になりました。
3. **matching_cost の要素を 64 ビットに詰め、貪欲法から分岐をなくした。** 要素は「鍵<<32 | 組<<16 | 2 つの注文」です。昇順に並べると、元の安定な並べ替えと同じ並びになります。
   - 貪欲の部分は 249 → 62 になりました。
4. **閉路の証拠を持たせた。** 組ごとに、関係に含まれる 3 枚の閉路の弧を覚えておきます。新しい関係がそれを含めば閉路があるので、閉包を計算しません。
   - 証拠はどんな閉路でもよいので、古くなっても判定は正しいままです。
   - 閉路が見つかった組は、今の関係と新しい関係の両方に含まれる閉路を新しい証拠にします（遅延更新）。
   - 閉包を計算する組は 1 評価あたり 163 → 80 になりました。
5. **閉包と表の参照を 2 段に分け、閉包を AVX2 で 4 組ずつ計算した（closure4）。** 関係の行列は pdep で作り、各ピボットはバイトのマスクで計算します。
   - 2 段化と証拠を入れた版（run 20261105-071841、96 seed）: map 0.707 → 0.576。証拠なしでは 0.589 でした。
   - CHD と遅延の証拠を加えた版（run 20261105-072718）: 0.676 → 0.501。
   - 未決の段全体は 762 → 238 になりました。
6. **swap_losses の閉包を減らした。** 最後の弧を失う選ばれた組は閉路を持たないので、外した後の閉包を計算せず、今の閉包から判定できます。
   - group_forbidden の表は 4 組ずつ、分岐なしで作るようにしました。
   - forbid の部分は 118 → 61 になりました。
7. **prepare_cross と make_transfer_options の閉包を 4 組ずつ計算した。** 対象の組は分岐なしで集めます。打ち切る位置と計数は元と同じです。
   - cross は 75 → 58、transfer は 48 → 38 になりました。
8. **表の作り方を変えた。** 双対の類のうち片方だけ番号を付け替え、値は 2 つの類の和にしました。双対の表 kPosetDual はオフラインで計算して埋め込んであります。
   - CHD のバケットは大きさで数え上げて並べます。
   - 表を作る時間は 23.1 → 9.4、準備全体は 41 → 21 になりました。
9. **細かい変更（それぞれ 1% 前後）。**
   - 窓の番号の剰余を定数で割る（g = 38/32/28 のとき）。
   - 温度（pow）は必要なときだけ計算する。
   - 窓の位置を表で引く。
   - k 番目の立っているビットを pdep で取る。
   - prepare_windows の表から分岐をなくす。

## 試して採らなかったもの

- **生きている組を含む 8 組のまとまりだけを評価する案。** 動かさない辺に両向きの弧を持つ組は、動かしても無効のままです。そこでそうした組だけのまとまり（全体の 38%）を飛ばし、受理したときに埋めるようにしました。
  - 出力は同じでしたが、まとまりごとの手間と受理時の埋め合わせで遅くなりました（3 seed × 3 回の中央値で 4322 → 4364）。
- **証拠を受理のたびに作り直す案。** 全組を見直すと、受理の時間が 9 → 400 になりました。変わった組の一覧を評価の中で作ると、評価が 90 遅くなりました。代わりに 4 の遅延更新にしました。

## 残り

窓の割り当ては 1 seed あたり約 1590 百万サイクル（約 0.44 秒）です。大きいのは次の 3 つです。
- evaluate_move の SIMD ループ（約 340）。毎回、近い組の全約 3430 組をなめます。
- matching_cost（約 340）。
- 未決の段（約 240）。
