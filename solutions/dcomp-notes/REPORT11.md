# Task 11: alt1 の要求探索と時間配分

**0.03%の採用基準には未達。alt1の置き換えは推奨しない。** 凍結候補 `dcomp-combo-dual25` は通常2000件で alt1 比 **−0.028115 ± 0.001881%**。未選別seed 500–1999の追加列1–3でも **−0.026093 ± 0.001219%**。GCCのjudge平均はargonの **1.078263倍**、p99差は+18.431 msで95%区間は0を含む。Clang native500のend差は **+0.080 ± 2.552 ms**で、速度差は確認できなかった。設定は最終確認前から変更していない。

副成果として、出力同一の `dcomp-combo-fast11` は通常500件で要求時間をGCC **34.775 ± 1.875 ms**、Clang **35.600 ± 2.153 ms**短縮した。これはスコアを変えない部品であり、今回の採用床を超える解法とは扱わない。

## 測定条件

基準は `solutions/dcomp-combo-alt1`。探索設定は seed 0–499 のみで選ぶ。要求側の試験は `20261108-155517_combo-m1-nine` の保存設計を読み、同じ4注文列で比較する。この設計は alt1 と全2000件で一致する。差は seed ごとの平均 log スコア比×100、±は seed 間の1標準誤差。負が改善。固定設計の req 差は同時比較の差としてだけ使い、judge の絶対時間には通常比較を使う。

すべての実行は `task10_run.py` → `scripts/pahcer_run.py`、24並列。ビルドと重い解析は共通 lock と nice の下で行う。GCC は既定の評価ビルド、Clang は native。コンパイラ間で探索予算を変えない。出力同一とは同じコンパイラで親と比較した stdout の全 byte 一致である。時間による切替・打切りは入れない。

全実験の run-id、スコア、時間差、出力一致件数は [TABLES11.md](TABLES11.md) にまとめた。再生成は `python3 solutions/dcomp-notes/task11_tables.py`。各 `task11_*_driver.sh` が実行条件、`t11-*.json` が解析値、対応する新解法の README が実装差分を保持する。

## 遅いケースの内訳

訓練500件だけを用い、通常実行の judge が遅い25件と req が遅い25件を別々に調べた。既存の通常 run `155517`（GCC）と `155242`（Clang）の比較、および新しい計測版 `162439` / `162556` に基づく。

GCC の judge 上位25件では、全500件平均より helper が約122 ms、req が約31.5 ms長い。map が約88 ms、anneal が約22 msを占める。Clang でも helper 約68 ms、req 約41 ms、うち map 約59 msである。したがって全体のtailは要求だけでは決まらない。

要求側のexclusive profileでは、next_cost が全体平均 → reqの遅い25件で GCC 56.9 →92.1 ms、Clang 51.7 →70.4 msとなる。他の大きな段はこの群でほぼ同じだった。列MDPが全列を覆わないケースの再走査が主因で、covered列の正確な紙ID列をキーにするキャッシュがここに効く。計測版には大きな計測負荷があるため、この表の絶対値から通常版の速度差を推定しない。

## 出力同一の高速化

採用候補は、anchorの固定配列と遅延anchorize、部分MDPの正確な列キャッシュ、next_cost初期化の遅延、合法性再生後のend-memo、修復区間の端点の直接計算。どれも浮動小数の加算順を保つ。数学的な条件とbit検査は [EXACTNESS11.md](EXACTNESS11.md)。

単体試験では、anchor遅延が GCC −8.32 / Clang −5.82 ms、部分MDPキャッシュが −1.87 / −2.83 ms、next_cost初期化が −4.37 / −2.93 ms、end-memo省略が −6.28 / −7.14 ms。部分MDPキャッシュは GCC の部分被覆40ケースでは −20.98 ± 2.43 ms、reqの遅い25件では −26.05 ± 3.26 msだった。キャッシュはキー全体を照合し、衝突時に値を共有しない。

合成版の通常GCC500件 `174110` は stdout 500/500一致。hash4版は req −17.93 ± 1.45 ms、end −14.10 ± 3.24 ms。memo省略版は req −19.79 ± 1.52 ms、end −11.35 ± 3.37 ms。後者のhelper差は +8.08 ± 2.85 msと出ており、単体の節約量を足し算して再投資枠にしない。最終候補の通常比較で検証する。

同じ合成版のClang native通常500件 `182512` も各500/500 byte一致。hash版はreq −12.41 ± 2.04 ms、end −16.32 ± 3.16 ms、memo省略版はreq −14.96 ± 2.01 ms、end −18.67 ± 3.19 ms。外部負荷は平均0.169 core、最大0.495 coreだった。

窓のpending列挙、closure共有、hole商テーブル、smallmovesなどは遅くなったため打ち切った。holeテーブルはTask 8でも失敗しており、今回の(n0,n1)キー版も同様だった。方向flagの直接bit展開も既存の失敗に近いため、一度の公正な比較で止める。

後半に二つのまとまった改善があった。end-memoを合法性再生の後へ移すと、不合法な試行のhashと有用entryの破棄を減らせる。GCC `193836` / Clang `194336` でreq −13.05 / −8.10 ms。完全な順序192byteを照合し、cache hitごとに元のcanonicalize・plan_costを再計算する検証も通した。

ejectのprofile `194212` / `194714` では、GCCのfirst/second窓所有位置表だけで約16.5 msあった。全128位置を作らず、必要な挿入区間の二つの端点だけをtop-two-layer prefixから求めると、GCC `200339` / Clang `200838` でreq −11.21 ± 1.59 / −5.64 ± 1.22 ms。各800/800 byte一致し、元の表と完全な紙順序を使った端点の全件照合も通った。

表示検査済み候補のリンク配列構築を省く変更は、GCCでは後段memoより速くならず、Clangだけで約4.1 ms短縮した。first-color探索の早期終了もClangだけで約3.8 ms短縮した。したがってこの二つはコンパイル時にClangだけへ選び、探索予算は共通にした。

## 修復してから比較する探索

raw候補の二重移動を結合してからfamily選別する変更は −0.005325 ± 0.000700%、req +5.762 ± 0.654 ms (`165437`)。従来は同じ移動紙列という理由で完成後に有利な候補を落とす場合がある。

joint fillerの区間DPで、同じ一次目的値なら広い取っ手区間を選ぶ規則は −0.007093 ± 0.000922%、req +2.494 ± 0.567 ms (`172757`)。計画数を増やさず、完成後の修復に入る構造を変える。weighted/complete-valueのDPは変えない。

完成済みの別ALT計画を中立探索の追加親にする試験は、gap .3、最大1個、元の6候補枠を共有して −0.013608 ± 0.001515%、req +31.147 ± 0.680 ms (`165437`)。追加親では1→1だけ列挙する版が −0.011895 ± 0.001438%、+23.087 ± 0.651 ms (`172023`)。追加親の候補枠、挿入時点、gapの制限も測定した。追加親は上位1候補を主親と共有し、1→1だけにする構成を最終版へ残した。

追加親の候補を上位1個に制限した版は −0.010517 ± 0.001368%、+17.359 ± 0.657 ms (`181808`)。最早の合法挿入だけにした版は −0.010819 ± 0.001370%、+18.609 ± 0.871 ms (`180503`)。gapを.15へ狭めるよりよい効率だった。合法試行が現在のbestを更新する時だけ二重移動を結合する案も −0.002484 ± 0.000445%、+2.267 ± 0.640 ms (`173953`) と小さな利益がある。

raw結合・広い区間の同点選択・追加親1→1をexact高速化と合成した `stack-one` は −0.025552 ± 0.001796%、req +6.487 ± 0.652 ms (`180636`)。通常post候補を6にすると −0.032447 ± 0.001896%、+24.682 ± 0.638 ms。中立幅を8/12とした別合成では −0.029455 / −0.032358%、+16.994 / +25.882 ms (`180835`)。単体の利得と時間を足した値ではなく、合成を再測定した値である。

同じ入力のpost_optimizeを再実行するprofile `183045` は200ケースで平均163/10,392呼出し、約5.91/356 ms。完全な呼出しcacheを作っても上限が小さいため、ここは実装へ進めなかった。

expanded候補の先行修復、neutral候補の事前修復、near-tie選択前の追加修復は改善に対して時間が大きい。raw上位8/12候補への安いdelete事前修復は改善を示さなかった。これらは深追いしない。

## 採否と残す部品

通常比較も追加注文列も改善は再現したが、0.03%に届かなかった。訓練上もっと強いpc6、slack .30などはClangの時間条件で落ちた。残るメニューの単純追加は費用が大きく、他の修復前選別・予測改善は2SE未満か費用に見合わなかった。最終評価を見て設定を選び直すことはせず、この凍結版で探索を終了する。

|残す選択肢|根拠と効果|時間|
|---|---|---|
|`dcomp-combo-fast11`|出力同一。GCC500、Clang500、GCC native200で全件byte一致|通常req −34.775/−35.600 ms (GCC/Clang)、end −28.780/−35.706 ms|
|`dcomp-combo-dual25`|通常2000で−0.028115±0.001881%。採用床未満の合成案|GCC req +0.252±1.047 ms、helper +6.006±1.771 ms。Clang endは同等|
|区間DPの幅による同点選択|単独の訓練500×4で−0.007093±0.000922%|req +2.494±0.567 ms|

単独の小さい利益を合成の利益へ加算しない。末尾のnear-tie pool全体を結合するmergepoolは単独−0.002327%だったが、既存の合成へ足しても改善しなかった。

次に進めるなら、検証済みの高速化を土台に、追加親からの候補生成や修復の重複処理をprofileして削る。単に探索幅を広げる案より、完成計画の別の出発点を安く作る方が今回の結果では有望だった。GCCではhelperの増分も残っており、ここは出力同一でも時間が変わる理由を切り分ける余地がある。現時点で0.03%以上の利益を約束できる未検証案はない。
