# chatgpt-joint-repair

改良元: `solutions/chatgpt-joint`

窓割り当てと 70 対の matching を同時に探索する構造は同じ。初版で窓が動きにくかった原因として、「選ばれた対を壊す窓変更の補修を 1/32 しか試さない」制限を疑い、その制限を外す。

## 変更点

1. **すべての窓提案で、最大 3 対までの喪失を許す。** 壊れた対を外し、同じ提案の中で補修してから目的値を比較する。既に 70 対を確保していれば 70 対へ戻すことが必須で、構成中は対数を減らさない計算済みの部分matchingも許す（末尾参照）。4 対以上壊れる提案は捨てる。
2. **未使用商品同士の辺だけで補えなければ、残った matching の辺を経由する長さ 3 の増加路を使う。** 自由端点同士を直接結べないことだけでは窓変更を諦めない。
3. **自由端点間の候補辺は 1 回だけ評価・ソートし、1 回の走査で必要な対を追加する。** 対を 1 本追加するたびに全候補を再計算しない。費用が同じなら対の ID 順にするため、逐次 greedy と同じ選択になる。
4. **補修の辺評価も増分計算する。** 現在の窓割り当てでの制約をキャッシュし、提案で変わる 1〜2 種類の arc 群だけ更新する。1 回の補修内でも、同じ辺は再計算しない。
5. **補修を制限する。** 1 回につき新しい辺評価は最大 4096、通常の時間制評価では倍率込み 2 ms を目安に打ち切る（新規辺評価 64 回ごと、増加路探索の matching 辺 8 本ごとに確認）。途中で打ち切った提案は採用しない。探索開始前の最初のmatching構成だけはこの局所補修制限の対象外。探索中の窓候補の補修には、70 対未満の構成途中でも適用する。`MAP_ITERS` を正値で固定した研究用比較では 2 ms 制限を外し、回数制限だけを使う。外側の時間確認は 32 提案ごとから 8 提案ごとにする。

目的関数、焼きなまし温度、窓／matching の近傍比率、最良 matching の後段への継承、列とハンドルの最適化、注文処理は改良元のまま。停滞時の脱出や多始点などは追加していない。

## 診断

改良元の診断値に加え、`repair_edge_evaluations` は初期構成と補修内で新たに計算した辺の数、`repair_work_limits` / `repair_time_limits` は回数／時間制限で補修を止めた回数、`repair_augmentations` は初期構成と、採用・不採用の提案を含む補修中に行った増加路の数。

`joint_map_accepts / joint_map_trials` と `joint_repairs_accepted / joint_repairs` により、補修制限を外して窓割り当てが実際に動くようになったかを確認できる。最良状態の独立再計算と matching／窓状態の assert は継承する。

## 初期構成と補修の区別

`complete` の戻り値を「70 対完成」「計算済みの部分 matching」「計算打ち切り」の 3 種に分ける。70 対に達する前の初期構成では、対数が減らない計算済みの部分 matching への窓変更を許す。70 対になった後は対数を維持する。時間・回数制限で計算途中になった候補はどの段階でも捨て、古い目的値のまま採用しない。初期版で「未完成」を一律に棄却していたため、初期対数が 70 未満のケースで窓と matching を少しずつ改善できない不具合を修正した。

`joint_repairs_accepted` は 70 対へ補修できた候補の受理数で、構成中に受理した部分matchingは含まない。通常の対話比較と、注文途中の時間による軽量化を外す `SIM_HARNESS` 比較の手順・解釈は [評価環境の説明](../chatgpt-study/README.md) を参照。
