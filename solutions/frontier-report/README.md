# AHC074: 汎用紙の表示関数とペアリングを同時に設計する

2026-11-01。比較基準は `df74cd2d8255b2f68d5c815a88b55238899177ec` の `solutions/imp-lean/`。
この文書は研究報告であり、提出解法の README ではない。

## 結論

**今回、imp-lean を上回ると実証できた解法はない。**
汎用紙を増やす案は実測で大きく悪化し、商品に二つの専用紙を持たせる後付けの案も、追加の修復費を回収できなかった。
6 枚のまま表示関数を変える試作は合法性を確認したが、通常の 70 ペアを固定すると 4 枚を使う新しい表示関数は採用されなかった。
新実装を現行提出版へ採用する根拠は得ていない。

今後検証する研究候補は、**汎用紙を動かす合法なグラフを保ち、各順序が表示する模様と、専用紙を共有する商品のペアを同時に最適化する方法**である。
これを有望と断定する実測はまだない。今回試した近傍・探索量では、既存ペアを全部守る後処理によって新しい表示関数を活用できなかった。
3 窓以上の同時変更や、一時的な悪化を許す探索の可能性まで否定した結果ではない。
共同設計を十分に探索しても総費用が下がらなければ、この方向も捨てる。

## 1. 現解法の何を変えるか

imp-lean は汎用紙 6 枚、汎用窓 36 個を使う。各汎用窓では、逆の色を持つ 2 枚のうち上にある紙の色を表示する。
6 枚の全 15 組を少なくとも一度ずつ比較するため、720 通りの順序を区別できる。
汎用層が露出している間は、最下段以外の 5 枚が必ずどこかで見える。
専用紙 186 枚は、70 個の共有ペアと 116 個の単独商品を担当する。
既存の最短距離表と注文処理は [imp-lean](../imp-lean/main.cpp) を参照。

既存の [trial_log](../../trial_log.md) の lat-probe では、1 注文約 10.73 手を、
持ち上げ 1.00、前の紙の処理 0.81、掘り 2.82、汎用紙 1.30、穴の修復 4.79 に分解している。
これは当該ログの計測値であり、今回のケースの内訳ではない。
また、これらは現行の構造に対する計測であり、問題全体の数学的な下界ではない。

今回変えたいのは、窓の表示関数を「2 枚のどちらが上か」に限定する部分である。
720 状態の BFS 自体は既存コードにある。新規の探索変数は、表示関数と、それに合わせて選び直すペアリングである。

## 2. 可視性と表示関数の分離

### 2.1 合法な移動を保つ 15 窓

6 枚の各組に対し、その 2 枚だけが逆の色で不透明な窓を 1 個ずつ保護する。
残り 21 窓を変えても、この 15 窓が残れば、露出した汎用層の最下段以外は必ず動かせる。
最下段の紙は、すべての窓を 2 枚以上が覆う限り見えない。
したがって今回のテンプレート集合では、合法な有向移動グラフとその距離表は元のままである。

この条件における 15 窓には理由がある。
単独の紙だけが不透明な窓を使わず、どの順序でも最下段以外を可視にしたいとする。
紙 a が下から 2 番目、紙 b が最下段にある順序で a を見せるには、a と b 以外をすべて穴にした窓が必要になる。
任意の組 a,b で同じ議論が成立するので、全 15 組が必要である。
これはこの可視性条件の下の導出であり、別の移動グラフを使う解法を排除する主張ではない。

### 2.2 残りの窓を選言的な順序条件にする

試作の窓テンプレートは次の 120 種類。

| 型 | 種類数 | 表示 1 の条件 |
|---|---:|---|
| 2 枚、黒 1・白 1 | 30 | 黒の紙が白の紙より上 |
| 4 枚、黒 2・白 2 | 90 | 黒の 2 枚の最上位が、白の 2 枚の最上位より上 |

黒紙を a,b、白紙を c,d、順序内の位置を pos とすると、4 枚窓は

\[
\min(\operatorname{pos}(a),\operatorname{pos}(b))
<\min(\operatorname{pos}(c),\operatorname{pos}(d))
\]

で 1 になる。これは

\[
(a<c\land a<d)\lor(b<c\land b<d)
\]

という条件なので、1 本の比較よりも複数の実現方法を持てる。
例えば 3 窓が a<b、b<c、c<a を要求すると実現不能だが、最後の条件を
`min(pos(c),pos(d)) < min(pos(a),pos(e))` に変えると、d<a<b<c<e で 1 側を実現できる。
反対側も e<c<b<a<d で実現できる。
これは選言の効果を示す小例であり、全商品を同時に安く実現できる証拠ではない。

### 2.3 増えるものと失うもの

表示できる完全な汎用パターン数は **720 のまま**である。
テンプレートが 30 から 120 種類になっても、表示パターン数が 4 倍になるわけではない。
変えられるのは、720 順序への表示の割り当てと、専用紙の穴へ射影したときの実現集合である。

2 枚比較は順序を逆転すると必ず補色になる。
4 枚窓では、上からの色が BWWB または WBBW のとき、逆転しても最上位の色が変わらない。
6 種類の色順のうち 2 種類、すなわち 1/3 では逆順と補色が対応しない。
15 個の比較窓をすべて反転する順序は元の逆順に一意に決まるため、4 枚窓を加えながら完全な符号集合の補色閉性をそのまま維持することはできない。
したがって、ペアの片側だけを検査する既存の DAG 判定をそのまま流用してはいけない。

## 3. 評価すべきものは許容状態の数より距離

商品 a,b の違う窓を D_ab、窓 j の表示関数を f_j とする。
共有専用紙は共通部分を印刷し、D_ab に穴を開ける。
商品 a の汎用要求を満たす順序集合は

\[
F_{ab}^{a}=\{\sigma\in S_6:
f_j(\sigma)=a_j\quad(j\in D_{ab}\cap G)\}
\]

となる。b 側も別に計算し、両方が非空でなければ共有できない。

合法な有向移動距離を d とすると、一様な開始状態に対する費用は

\[
C(F)=\frac1{720}\sum_{s\in S_6}\min_{t\in F}d(s,t).
\]

同じ個数の実現状態でも、それらが近くに固まっているか、離れて分布しているかで費用は異なる。
実現状態の個数や整合する商品のペア数だけを目的にしない。
非負整数距離の期待値の恒等式から、

\[
C(F)=\sum_{\ell\ge0}\left[
1-\frac{|\{s:\exists t\in F,\ d(s,t)\le\ell\}|}{720}
\right]
\]

とも書ける。目標集合が合法移動グラフをどれだけ短距離で覆うか、という評価になる。

この C は一様状態の厳密な距離平均であり、実際の注文列の定常分布や、穴埋めとの相互作用まで厳密に解いた値ではない。
実際の採用判断には同じ入力での手数比較が必要である。

## 4. 今回実装した部分と、次の段階

[frontier-lattice](../frontier-lattice/README.md) は、既存の 70 ペアを固定した小さい試作である。
各比較辺の保護窓を 1 つ決め、残りの 1 窓、または同じ元の比較辺を担当する 2 窓を変える。
全 140 側の要求を維持し、C の合計が厳密に減る変更だけを採用する。
許容状態集合は 720 bit、距離は元の全点対 BFS 表を使う。
表示を変更した場合のオンライン処理も、新しい実現集合への最短経路を求める。

64 ケースでは、変更を採択したのは seed 5024、5025 の各 1 回だけで、どちらも **2 枚比較のままの変更**だった。
4 枚窓は全ケースで 0 個、4 枚窓に触れる注文も 0 件。
新しい表示関数の有効性を実測できたとは言えない。
10 ペアだけの内部 fixture では 4 枚窓を含む採択分岐を実行できたが、これは実装検査であり得点改善の証拠にしない。

### 次に実装するなら

次に試したいのは、ペアも探索変数にすることである。
テンプレート変更で一部の既存ペアが壊れることを許し、自由になった商品と単独商品を再マッチングする。
70 個の互いに素なペアという制約は維持する。
候補の評価には、両側の C に加えて、列への配置、掘り、ハンドルの穴修復の費用を含める。
例えば、変更で壊れたペアから始める長さ 3・5 の増加路や交換路で修復し、総費用が下がるかを判定する。

```
現在の表示関数、70 ペア、列配置を持つ
1〜2 窓の表示関数の変更を提案する
影響する商品の両側の実現集合を更新する
壊れたペアを解放し、単独商品を含む集合でペアリングを修復する
新しいペアの generic 費用と、列・穴の費用を再計算する
総費用で採否を決める
```

最初から 2 秒への高速化を目標にするより、設計計算に余裕を与えた研究版で
「元は汎用層で非整合だった、ハンドル側で近いペアを採用し、総手数が下がる」例が継続して出るかを調べる。
ここで利益が出なければ高速化する理由はない。
利益が出る場合だけ、変更窓を除いた実現集合のキャッシュ、bitset の差分更新、増加路候補の限定を行う。

今回、共同再マッチングは未実装である。
この手順は次段階の設計案であり、今回の比較結果へ効果を含めていない。

## 6. 二重表現の利益に関する補足

長さ n の循環列で、同じ商品を距離 g 離れた 2 枚から取り出せるとする。
開始位置が一様、追加の修復費が 0 なら、最良の半周配置は平均 n/4 手を節約できる。
ただしこれはその商品の取り出しだけの値であり、全注文の平均ではない。

追加表現の修復費が δ_b ≥ 0 のとき、連続緩和した最良の利益は

\[
B_{\max}=\frac{(n-\delta_b)_+^2}{4n}.
\]

単独商品 a の紙を共有紙 (a,b) に変える費用を δ_a とすると、利益が出るには δ_a < B_max が必要。
δ_a=δ_b=δ の単純化では n > (3+2√2)δ が必要になる。
すでに共有紙を持つ b を選び δ_b≈0 にできても、n > 4δ_a が要る。
実際の列は色合わせや挿入で変わるため、これは理想化した循環模型の条件である。
[frontier-math](../frontier-math/README.md) に導出と検算を置いた。

## 7. 検証と再現性

- 問題文と公式 Rust ツールの入力分布を読み、独立に 128 ケースを生成した。各バーコードは 64 窓中 32 個が 1、256 種は相異なり、注文は直前の商品を除いて一様。
- 入力の末尾にある未来の注文列はテスターだけが読み、解法には注文を 1 件ずつ渡した。
- Python の乱数を使うので、例えば seed 5004 は公式 Rust 生成器の seed 5004 と同じ入力ではない。入力の SHA-256 は [生成 manifest](../frontier-eval/generated-5000-5128.json) に保存した。
- Rust toolchain がなかったため、公式規則を移植した C++ テスターを使用。公式 Rust バイナリとの直接照合はしていない。43 個の既知・ランダム fixture を独立実装の `scripts/replay.py` と照合した。
- 比較は既存 `scripts/pahcer_run.py` の `evaluate_compare` を呼び、同じ seed ごとに全解法を順番を交替して実行。共通スクリプトは変更していない。
- コンパイルは `g++ -std=c++23 -O2 -DCLOCK_SCALE=1.1`、4 並列。この環境と AtCoder の速度は未較正で、ジャッジでの時間内完走を保証するものではない。
- 上の主要 8 run、計 320 個の解法×ケースについて、全 1024 注文の合法な replay、得点、E/T の恒等式、出力の長さとハッシュが一致した。誤表示・WA・実 wall 2 秒超えは 0。
- 最初の試行で保存ログが途中状態になった run 群 `20261101-050047_*` と `20261101-051539_*` は結果から除外し、同じ入力で比較をやり直した。後者から都合の良いケースだけを採用することはしていない。
- ログはメモリに全量取得し、完了後の atomic rename で保存するように評価補助だけを修正した。64 ケース比較では採点に用いた stdout/stderr の SHA-256 と保存ファイルも一致した。
- [check_lattice.cpp](../frontier-lattice/check_lattice.cpp) は採択分岐の全再計算一致と、4 枚窓を含む設計の全 720 開始順からの合法性・最短距離・最終表示を検査する。これを得点評価とは区別した。

主要結果の各ケースの値とソースのハッシュは [results](results/) に保存した。
全 stdout/err は通常の `runs/` にあり、リポジトリの規約どおり git 管理の対象外。
