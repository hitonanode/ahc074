# D3：未被覆列のColumn MDP

助言01-3「Column MDPの全列カバレッジ化」をPR146に対して検証する。
BASE.mdの2026-11-06 07:00新方針（採用0.03%、失敗時の改訂は1回まで）を適用する。

## 原因

`Column MDP: long-run values of the order of a column` の `ColumnMdp::build` は、
長さ14、完全順列40000、全部分列250000を上限とする。
保存設計 `20261106-062412_argon-des-perf-latew105` の2000件を独立に読み、
種類別枚数から多項係数を厳密に合計した（`limits.py` / `limits.json`）。

- 未被覆は212ケース・214列（全25列被覆1788、24列210、23列2ケース）。
- **長さ制限は0列。全列の長さは3〜12。**
- 完全順列の上限だけが143列、完全順列と部分列の両方が71列。
- 未被覆列の最大は207900完全状態・636753部分列。

従って「長い列が使えない」という説明は今の設計には当てはまらず、
正確には4種類の紙の混合により状態数が増えた列が対象となる。
保存設計だけを用い、入力の未来の注文は読んでいない。

## 全列を被覆する対照

`argon-des-colmdp-full` は既定上限だけを250000完全状態・800000部分列へ変更。
長さ14、価値反復8回、混合係数、注文処理の他の部分は基準と同じ。
状態を切り捨てる近似を作る前に、元の型列MDPを全列に適用した効果を測る。

固定設計200×2、run `20261106-071307_argon-des-perf-latew105` /
`20261106-071307_argon-des-colmdp-full` では−0.000517±0.001298%、11/178/11。
未被覆だった22ケースに限ると−0.004700±0.012007%、11/0/11。
従来から全列被覆の178ケースは全て同点。両群WAなし。
全212ケースの効果を確かめるため、同じrunを2000×2へ延長した（結果は下記）。

DesignStore読込時には設計終了時刻が保存値へ復元されるため、固定設計のjudge値には
増えたMDP構築時間が反映されない。構築負担は`colmdp_sec`で別に読む。
採用可能な効果が出た場合だけ、通常比較で全体時間を確認する。

## 2000×2の結論：未採用

同じrunを全2000件へ延長。平均log比 **-0.000879±0.000619%**、
勝/分/敗 **109/1789/102**。影響する212件では
-0.008294±0.005826%、109/1/102。
残り1788件は同点。全列被覆25.0列を確認し、WA・self_wrong・op_label_errorsは全て0。

MDP構築時間は0.009750→0.014977秒、
差+5.226±0.282 ms。
req_secは0.449504→0.445009秒（差-4.495 ms）。
固定設計の形式的judge値は、基準mean/p99/max/>2秒 =
1.603388/1.766671/1.873319/0、
候補は1.597268/1.758466/1.880468/0。
前述の通り追加構築時間を含まないので、通常比較のjudge評価としては使わない。
初期200件の外部負荷0.22/0.54、追加1800件0.18/0.42コア（平均/最大）。

改善側の95%上限は約0.002092%で、0.03%に遠い。
厳密な型列MDPを適用した対照そのものがほぼ同点であるため、
その計算を省略する近似状態の実装は行わない。これはあらゆる列の価値モデルの上限証明ではなく、
今回の「既存MDPの被覆を増やす」という指摘の効果を直接測った判定である。
効果がないため通常2000件の採用比較は行わず、D3を終了する。

`argon-des-colmdp-full`はGCC/Clang・C++23 O2 Wall/Wextra・LOCAL_BENCH有無の
4構成で警告・エラーなし。コマンド・SHA256は同ディレクトリの`build-results.json`、
ログは`build-*.log`。主ディレクトリのmain.cppは基準と同一。
既存の指標・スイッチ・段と目次を保持し、コンパイル済みバイナリは削除済み。
