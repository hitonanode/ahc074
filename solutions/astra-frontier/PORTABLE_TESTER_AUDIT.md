# ポータブルテスターの独立監査

対象は `portable_tester.cpp` の buffered relay 版（子の stderr を専用スレッドで読み、
子の終了後に stdout・stderr をまとめて保存する版）。
比較元はリポジトリの `tools/src/lib.rs` と `tools/src/bin/tester.rs`。
この監査はソースの静的比較であり、Rust 実行環境での差分実行を行ったとは主張しない。

## 結論

**今回の各解法が出力する ASCII・応答末尾改行・正常終了という範囲で、
整数スコアへ影響する規則の相違は見つからなかった。**
一般の異常な出力まで含む完全な同一実装ではないため、以下に相違の範囲を示す。
最終評価ではこれに加え、保存された全出力を既存 `scripts/replay.py` で再生し、
合法性・全注文の正誤・整数スコアの一致を要求する。

## 規則ごとの比較

|項目|監査結果|
|---|---|
|事前入力|両方とも N/K/P/R と P 個の商品だけを子へ送る。紙の設計を読み終えるまでは注文を送らない。|
|将来の注文|両方とも現在の注文に対する全操作を読み終えた後で次の注文を一つ送る。親が全注文を保持していても、子の stdin に将来注文を一括投入しない。|
|紙の設計|長さ N、文字 `0/1/.`、K 枚を検査する。不透明・黒のビット番号は左から j 番目を bit j として一致する。|
|操作数|両方とも 0〜2K を含む。C++ の `number(2*k+1)` は同じ範囲。|
|紙番号・深さ|両方とも 0〜K−1。C++ の `number(k)` は同じ範囲。|
|可視性|対象紙の不透明マスクから、その上の紙の不透明マスクを順に除く。一ビット以上残ることを要求する。全穴の紙を動かすことは両方で不正。|
|挿入位置|pos<d の左回転、pos>=d の右回転は、Rust の inclusive slice と C++ の half-open iterator 範囲で一致する。対象紙は操作後の位置 d に置かれる。pos=d も一手として数える。|
|表示|上から最初の不透明紙の色。覆われない窓は白。Rust の全窓被覆時の早期終了を C++ は省くが、その後の寄与はゼロなので表示は同じ。|
|誤注文|各注文の最終表示と要求バーコードを比較し、一窓以上違えば一回だけ誤りを加える。次の注文にはそのまま現在の順序を引き継ぐ。|
|スコア|両方とも `2*K*mistakes + moves`。本番 K=192 では誤注文一回384手分。|
|途中 EOF・範囲外・不可視操作|両方とも不正として Score=0。エラー文の文言には差があるが得点は同じ。|
|最後の余分な出力|空白以外の余分な token があれば両方で Score=0。ASCII の空白だけの末尾は両方で許される。|
|異常終了|正しい最終出力があっても、シグナル終了・非ゼロ終了は C++ 側でも Score=0 にする。保存出力の再生だけでは検出できない異常を子の終了状態で検査する。|

`number()` の整数演算は、各桁で値を小さい上限未満に制限してから次の桁へ進む。
従って本問題の上限では、長い数値によるオーバーフローで範囲検査を抜けることはない。

## 一般の出力に対して残る相違

1. **改行前の token の確定。** Rust は `read_line` で改行または EOF を待ってから token 化する。
   C++ は ASCII 空白を読めば token を確定する。このため、解法が「末尾をスペースだけにして flush し、
   次の入力を待つ」という改行義務違反をすると、C++ では進み、Rust では停止する可能性がある。
   今回の解法は設計・操作列とも改行を付けて flush するので、この違いを利用していない。
2. **Unicode 空白。** Rust の `split_whitespace()` は Unicode の空白も扱う。
   C++ は通常の ASCII 空白六種類だけを扱うため、Unicode 空白で区切った出力を拒否する場合がある。
   今回の数値・模様の出力は ASCII のみ。
3. **極端に長い token。** C++ は 100000 byte を超える token を拒否する。
   Rust にはこの上限がないため、例えば極端に長い先頭ゼロ列の扱いは一致しない。
   今回の出力には該当しない。
4. **テスター自身の終了コード。** 子が異常終了したとき、Rust の tester は終了コード1を使うが、
   C++ は判定を stderr に出して終了コード0を返す。双方の判定は Score=0。
   使用している `pahcer_run.py::compare_case` は子テスターの終了コードで得点を上書きせず、
   最後の `Score = ...` を読んでいるので、今回のスコア集計には差がない。

これらの相違があるため、この移植を無条件に公式テスターと同一とは記載しない。
今回の解法が使う通常の入出力についての規則一致と、独立再生の一致を根拠とする。

## buffered relay と時間の扱い

stdout の保存時刻を遅らせても、子との対話用パイプは別に読み書きしている。
したがって、現在の注文を送る時刻の条件や将来注文の非公開性は変わらない。
stderr の読取スレッドはそれだけが文字列へ追記し、親は `join()` 後に保存するため、
この文字列に対する同時アクセス競合はない。

両テスター自体は AtCoder の二秒制限を実施していない。
`pahcer_run.py` の実行時間はテスターの処理・プロセス起動・保存の時間を含む壁時計であり、
buffered relay・`fsync`・ホスト性能の影響がある。
従って整数スコアの整合性と、AtCoder 上の実行時間の保証を混同しない。
二秒を超える仕事量固定の診断は、提出可能な結果とは別に報告する。

既存の七つの小さい protocol fixture は正常操作、誤表示、不可視操作、余分な出力、
操作数超過、途中 EOF、正常な最終出力後のクラッシュを検査する。
本監査中は評価と競合する追加実行や、テスター本体の変更を行っていない。
