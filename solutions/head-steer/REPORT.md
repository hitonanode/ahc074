# 列先頭の価値による設計探索の改善

**推奨は `main.cpp` の「棄却キャッシュ＋先頭資格による不要計算の除去＋４倍 climb」。1000件×４注文列で基準比 −0.0231 ± 0.0066%、climb は基準より39.6%短く、窓割り当て後の設計処理全体も3.0%短くなった。焼きなましへ近似目的を入れる２案は改善を確認できず、不採用。**

比較基準は `solutions/dsel-probe`、`CLIMB_LAMBDA=0.5`。注文処理は全候補で同じ。
設計の変更を含むため、各候補が自分で生成・保存した設計を４本の共通注文列で評価した。
差は seed ごとに４本の `100 log(candidate/base)` を平均し、その seed 間平均と標準誤差（SE）を示す。負が改善。
基準の保存設計は `20261105-005904_dsel-probe`、４注文列の基準は `20261105-010030_dsel-probe`。
評価はすべて `scripts/pahcer_run.py ... --no-record`。共有ソース、pahcer、trial_log は編集していない。

## 機構１: 古くならない短区間の head-aware annealing

`anneal.cpp` に保存した実験。既存の AVX2 焼きなましの４区間のうち、後ろ３区間の最後の 1/16 を、同種・色保持の交換だけに置き換える。全反復数は約1490万回のまま。つまり全体の 4.69% が限定した探索となる。

この交換は列ごとの単位数、ターゲット数、各色の枚数、各色の最大の重みを保つ。ペア構成とハンドル順も固定する。これにより、次の表が別の紙や別のハンドルを評価してしまう問題を避けた。

- **Donor 項:** 各単位を各列に置いたときの `filler_gain` を、区間開始時のターゲット位置で合計する。各列・各色の先頭資格（ペア優先）を持つ紙の最大効用に、開始時の head-color probability を掛ける。区間内では列の候補の最大値を更新する。
- **Recipient 項:** 開始時の各列・各色の最良先頭紙を固定し、移動する単位のターゲットが各列へ移ったときに得る穴埋め効用を表にする。
- ２項の差を合わせて双方が動く効果を一次近似し、`model_cost − 0.5 × surrogate` で受理・最良状態の選択を行う。0.5 は安全な交換で既に測られた climb の因果的な重みに合わせた。
- 各手では表参照と２列の最大値の計算だけを追加する。全ターゲットの走査は３回の表作成時だけ。

初版の表作成は約0.040秒かかった。各色の最大の重みはこの区間で不変なので、先頭資格を得ない紙の行を計算する必要がない。これを省くと約0.015秒になった。保存設計は初版と200件すべて一致し、同時比較の焼きなまし時間は基準 0.56040秒 → 0.58604秒（+4.58%）になった。

ターゲット側の一次近似の影響を分けるため、Recipient 項だけを省く機構の比較も行った。重みの網羅的な探索は行っていない。

## 機構２: 棄却キャッシュと、先頭資格による不要計算の除去

`main.cpp` の候補。filler climb が同じ状態で同じ２単位の交換を再び引いても、結果は変わらない。棄却を２単位の組と世代番号で記憶し、同じ世代の再計算を省く。交換の受理が１回でも起きたら世代を進め、すべての記録を無効にする。動いたターゲットは離れた列の紙の効用も変えるので、局所的な無効化にはしていない。

乱数を引く回数と順序は保つ。目的関数、受理条件、交換候補は変更しない。したがって探索経路を変える近似ではなく、同一状態で繰り返す計算の除去である。これを使って、既に伸びしろが確認されている 38,500 → 154,000 回の climb を安く実行する。

200件の予備評価では、4倍 climb の有効な候補約12,376回のうち約7,897回（63.8%）の再計算を省き、実際の計算は約4,479回だった。受理は14.07回。保存設計の全構造は、キャッシュなしの既存4倍版 `20261105-004243_dsel-probe` と200件すべて一致した。

キャッシュだけでは基準に約0.027秒の追加時間が残ったため、先頭の資格を持たない紙の効用計算も省いた。安全な交換は列・色・種類ごとの枚数を保つので、各列・各色の先頭資格の条件は不変である。今の列で資格のない紙の効用は最大値に寄与せず、保持・更新する必要がない。その紙が移動したときは移動先の資格を確認し、必要なら全ターゲットから効用を計算し直す。ターゲットとしての寄与は省かない。したがって proxy も探索経路も変わらない。`CLIMB_PROXY_MEAN=1` では全紙が寄与するので、この省略は行わない。

この２段の不要計算除去で、質の向上が既に分かっている４倍の探索を、通常の１倍 climb の時間内へ収めることが狙いである。利得の源は反復数の増加であり、重みの再調整や受理判定の近似ではない。

## 模型費用と最終 proxy

`model_cost` は stderr、`proxy_final` は既存の `dsel-probe/proxy.py` を保存設計に適用した値。焼きなまし直後の proxy と、再割り当て・穴あけ後の保存設計の proxy は区別する。

| 設計 | 件数 | model_cost | proxy_final |
|---|---:|---:|---:|
| 基準 | 200 | 8.237417 | 0.606333 |
| Donor + Recipient | 200 | 8.239128 | 0.609923 |
| Donor-only | 200 | 8.239016 | 0.611650 |
| 基準 | 1000 | 8.238054 | 0.608102 |
| 最終版 | 1000 | 8.238833 | 0.613297 |

最終版の差は model_cost +0.000779 ± 0.000266、proxy +0.005195 ± 0.000406。したがって `J = model_cost − 0.5 proxy` の平均差は −0.001818。模型の列費用は全件不変。climb の平均受理数は12.157 → 15.032、climb 自体の proxy は0.537094 → 0.544313だった。重複計算を省いて同じ時間でより深く探索でき、少しの模型費用増より大きい先頭価値の改善を得ている。実際の４注文列でも手数が減るため、proxy だけの改善ではない。

焼きなまし案の Donor + Recipient は、climb 前の proxy を基準より +0.047860 上げたが、climb 後の差は +0.007806、保存設計では +0.003590 ± 0.002202に縮む。模型費用は +0.001711 ± 0.001307。改善の多くが既存の後段処理の前倒しになっており、最終的な利得を確認できなかった。Donor-only も最終 proxy を増やしたが実スコアの改善にはつながっていない。どちらも200件では差が2 SE未満であり、悪化が確定したとは扱わない。

## 検証と推奨

- 最終版の保存設計1000件すべてで、全 DesignState と `helpers_ready` が、キャッシュなしの既存４倍 climb `20261105-004243_dsel-probe` と一致。
- 1000件×４注文列のスコア4000個も、既存４倍版の注文評価 `20261105-004534_dsel-probe` とすべて一致。省いた計算が設計や注文処理を変えないことを確認した。
- 最終 main.cpp は GCC / Clang の C++23 ビルドを確認。GCC の通常1000件と、最終設計の４注文列評価は WA 0。
- `main.cpp` を次の解法へ取り込むことを推奨する。差分は filler climb の不要計算除去、既定反復数154,000、既定 λ=0.5、計測指標だけ。注文処理は変更していない。
- `anneal.cpp` は比較用に残すが、不採用。今回の範囲では「焼きなまし自体が良い先頭の設計へ収束する」利得は得られなかった。

```sh

python3 scripts/pahcer_run.py solutions/head-steer --design-from CANDIDATE_DESIGN_RUN --orders 4 --seeds 0-1000 --no-record -c 'cache4 orders'
/home/sato/ahc074/.venv/bin/python -B solutions/dsel-probe/pair_compare.py 20261105-010030_dsel-probe CANDIDATE_ORDERS_RUN

# anneal.cpp: Donor + Recipient / Donor-only の独立した保存設計
HEAD_RECIPIENT=1 python3 scripts/pahcer_run.py solutions/head-steer/anneal.cpp --seeds 0-200 --save-design --no-record -c 'head-aware tails'
# 同じコマンドの HEAD_RECIPIENT=0 が Donor-only
```

`analyze.py --proxy` は既存の `solutions/dsel-probe/proxy.py` の関数をそのまま呼び、最終設計の proxy を再計算する。分析結果のキャッシュは head-steer 内だけに置く。最終版とキャッシュのみの版は全設計が一致したため、1000件の計算済み proxy も共有した。分析中に評価へ負荷を掛けないよう `runs/.lock` を取得して実行した。
