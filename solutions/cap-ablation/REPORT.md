# cap の除去実験

## 比較の範囲

改良元は `solutions/assign-search`（PR #131）。別セッションの設計構造・cap位置・多様性の研究には変更を加えず、固定capを完全に除くablationを行う。query-memoの変更は入れない。

| 解法 | cap | 汎用窓 G | ハンドル窓 H | 商品紙 | 対 / 単独目標 |
|---|---:|---:|---:|---:|---:|
| assign-search | あり | 38 | 25 | 185 | 71 / 114 |
| cap-ablation | なし | 38 | 26 | 186 | 70 / 116 |
| cap-ablation-g39 | なし | 39 | 25 | 186 | 70 / 116 |

capなしでは物理窓63も交換・極性・汎用/ハンドル割り当ての対象にする。設計のペア数・ハンドル数を変え、capに専用だった紙6を商品紙へ戻す。商品紙は常に最上部へ持ち上げる。通常のcanonicalizeと高速canonicalize、補助紙挿入の深さ、後処理のcap越え禁止、移動候補からのcap除外、初期順序と出力番号変換を更新した。フィラー需要・滞留価値・穴あけの走査も紙6を含める。

窓割り当て450000回＋133000歩、設計焼きなまし14900000回、filler climb154000回などの回数・重み・注文探索は元の値。`CAP_G` は既定38または39で、比較では環境変数を指定しない。通常の実験スイッチ・指標・プロファイラは保持する。`cap_window=-1` はcapなし。DesignStoreの64窓設計の保存/読み込みを維持し、capありの63窓設計の誤読を拒否する。

## 検証と結果

全実験は `scripts/pahcer_run.py` から実施し、`--no-record` は使用しない。設計が変わるため比較は通常の入力で行う。設計を保存し、`analyze_design.py` で各対のハンドル差、商品紙のハンドル穴、三角形の穴と対の差による穴を集計する。

差は候補 / cap付きassign-searchのケースごとの平均log比（%、正が悪化）、±は標準誤差。勝/分/敗は候補側。各行の時間は同一compareで測定した平均である。全run-idは接頭辞 `20261105-124053` に `_assign-search` / `_cap-ablation` / `_cap-ablation-g39` を付ける。

## 2000 seedsの確認

run-id: `20261105-124053_assign-search` / `20261105-124053_cap-ablation`（500→2000へextend）。G=39の版は500件で停止。

- 平均log比 **+0.196929 ± 0.026794%**、勝/分/敗 **857/2/1141**。
- 平均手数 **10338.6095 → 10358.9805**（除去で20.371手/ケース増）。
- `map_end_sec` **0.462586 → 0.486307秒（1.05128倍）**。
- `helper_end_sec` **1.078188 → 1.109811秒（1.02933倍）**。
- `req_sec` **0.357696 → 0.362654秒（1.01386倍）**。
- `end_sec` 平均 **1.449655 → 1.486578秒（1.02547倍）**、99%点 **1.67031 → 1.70915秒**、最大 **2.23427 → 2.24903秒**。
- `end_sec > 1.8 / 1.9 / 2.0` は **5/4/1 → 4/2/1**。2秒超えの件数は同じだがケースは異なる。capなしのseed 509は2.24903秒（基準の同seedは1.92434秒）。時間超過が消える変更ではない。
- **WA=0、self_wrong=0、op_label_errors=0**。全2000件で商品紙186枚・70対・G38/H26。評価外負荷は拡張時に平均0.17コア・最大1.26コア。

## 結論

**capは現在のベースでも有効で、維持を推奨する。** 指定された2つのno-cap構成はいずれも500件で悪化し、そのうち良かったG38でも2000件で約 **0.197 ± 0.027%** 悪化した。G38では平均時間も約2.5%増える。G39は500件で速くなったが約0.269 ± 0.052%悪化した。これはこの2構成のablationの結論であり、任意のno-cap設計がcap付きより悪いという主張ではない。

## 実装の最終確認

- G38の2000設計で、物理窓63は汎用窓1182件・ハンドル窓818件。G39の500設計では310件・190件で、窓63の特別扱いは残っていない。
- query-memo / cap-ablation / cap-ablation-g39の3版を `g++` / `clang++`、`-std=c++23 -O2 -Wall -Wextra`、`LOCAL_BENCH`あり/なしの全12通りでビルド。全て成功・警告0。コンパイル中も共有評価ロックを保持し、評価と重ねていない。
- G38設計の読み込み: `20261105-125303_cap-ablation` / `20261105-125303_cap-ablation-g39`、seeds 0–7。両プログラムが保存されたG38を使用し0/8/0、各出力は元の通常runの8出力とバイト一致。
- G39設計の読み込み: `20261105-125358_cap-ablation-g39`、seeds 0–7。元の通常runの8出力と全件バイト一致。読み込み確認もWA・self_wrong・op_label_errorsは0、design_loaded=1。
- ソース変更は新設のquery-memo / query-memo-template / cap-ablation / cap-ablation-g39内のみ。コミットしていない。通常runは全てpahcer登録済み。
