# 選択的な穴加工による補助紙の再利用：解法・検証報告

2026-11-02（日本時間）。基準は `800a3030278849158ada3ede2f41401bb72af3d8` の `solutions/imp-gla/main.cpp`。

## 結論

新しく検証できたのは、**専用紙の一部を穴に変え、その紙を別の商品対の補助紙としても使うと、汎用6枚だけでは表せなかった商品対を扱える**という設計の自由度である。これは単に汎用層の探索回数を増やす変更とは異なり、対を作れる条件そのものを緩める。

ただし、現在の提出用実装が `imp-gla` より強いという結果は得られていない。1組だけ導入する版の、同一初期設計からの96件比較は **+0.128% ± 0.037% SE、33勝0分63敗**で悪化した。さらに、加工を複数組で共有する版まで実装したが、未使用64件で **+0.616% ± 0.075%、10勝0分54敗**だった。誤った注文と不正操作はいずれも0。局所的な表示可能性の拡大を、操作数の改善と混同してはいけない。

このPRは実験と検討を引き継ぐためのもの。既存の解法・共通評価スクリプトは変更しない。主な読む順序は次のとおり。

1. 本報告：数学的な着眼点、実スコア、限界、次の判断。
2. [`../astra-options/RESEARCH.md`](../astra-options/RESEARCH.md)：表示可能性の全列挙と独立照合。
3. [`../astrasearch-perforated-union/main.cpp`](../astrasearch-perforated-union/main.cpp)：最大1交換の提出用C++23実装。
4. [`results/`](results/)：全比較のケース別スコア、時間、ソース・入力・出力のSHA256。

## 1. 何を変えるのか

### 現構成で強い制約になっていること

基準解法は、36個の汎用窓G、28個のハンドル窓H、汎用紙6枚と専用紙186枚を使う。専用紙の内訳は70枚の2商品共有紙と116枚の単独商品紙で、合計256商品を表す。

各G窓は、逆の色を持つ2枚の汎用紙の上下で決まる。ある商品の要求する色は6頂点の順序制約になり、その有向グラフがDAGなら表示できる。専用紙を共有する2商品は、色が異なる窓を穴にし、Gの穴を汎用層、Hの穴をハンドル側の修正で表示する。

このとき「差分が小さい良い商品対」であっても、Gで要求する順序制約に閉路があると、通常の共有紙にはできない。最適化を強くしても、この不適合な対は探索空間に入らない。

### 専用紙の役割を1つに固定しない

既存の専用紙Xを汎用層の途中へ挿すと、Xが正しい色で覆う窓では比較器の順序制約が不要になる。ただし、Xが誤色を出す窓が残ると使えない。

そこで、**誤色になる一部のセルだけを穴にする**。Xを専用紙として使う元の商品も引き続き表示できる範囲で、GとHに穴を追加する。自身を取り出すための所属列のハンドルは必ず保持する。

この変更では、専用紙Xは「元の商品を表示する主紙」と「別の対の順序制約を取り除く補助紙」の両方を担う。穴加工には、元の商品で穴を修正する手数が増える代価がある。その代価よりも、新しい対と配置の利益が大きいかが最適化の対象になる。

## 2. 表示可能性を64集合で正確に判定する

商品uとvの共有紙Dを作り、G上の差分を `gh = (A[u] xor A[v]) & G` とする。補助紙Xの不透明マスクを `X.opaque`、黒マスクを `X.black` と書く。

汎用紙のうちXより上にある集合Sは64通り。Sのいずれかが覆う窓のマスクを `C[S]` とすると、Sの下から見えてしまうXの誤色は次になる。

```text
badG = (X.black xor A[u]) & X.opaque & gh & ~C[S]
```

`badG` を穴にした後で、汎用紙による表示が必要な窓は次になる。

```text
need = gh & (C[S] | ~X.opaque | badG)
```

`need` の各窓が要求する比較器の辺と、「Sの全紙はS以外の全紙より上」という辺を合わせる。このグラフがDAGであることが、現在の6枚比較器・1枚の補助紙・指定したSと穴加工のもとで、対象のG穴を表示できる必要十分条件となる。全64窓の表示や紙の取得経路までの条件ではない。実装ではさらに、Xの元の担当商品それぞれについて、元のG穴と追加G穴を合わせた要求グラフがDAGかを独立に確認する。

元の商品が2つある場合も、片方だけを調べて順序を反転する方法にはしない。追加穴では2商品の色が等しいこともあり、元の共有紙の差分穴だけに成り立つ補色性を使えないためである。

Hで誤色になるセルも穴にする。ただしXの自身のハンドルに誤色が出る候補は棄却する。最初の1交換版はu方向とv方向に別々の補助紙を選び、同じ紙への相反する加工を避ける。

判定の実装とは別に、Pythonで汎用720順序を直接列挙して6,400方向の構成を照合した。DAG、元の担当商品の再表示、Hの色、自身のハンドル保持のすべてが一致した。詳細と再現手順は `astra-options` にある。

## 3. 表示可能な対は大幅に増えた

基準の8設計から、単独商品の組で、全64窓のHamming距離が26以下、かつ汎用6枚だけでは対にできないものを集めた。対象は計5,415対。共通紙を置く列は28列を試し、その列の自身のハンドルでuとvが一致することを要求した。

| 許す加工と補助紙 | 救済できる対 / 5,415 | 両方向に浅い補助紙がある対 |
|---|---:|---:|
| 加工なし、全既存紙 | 45 | 32 |
| Hだけ穴化、単独商品紙のみ | 99 | 1 |
| Hだけ穴化、全既存紙 | 522 | 258 |
| HとGを穴化、単独商品紙のみ | 5,415 | 1,385 |
| HとGを穴化、全既存紙 | 5,415 | 2,336 |

「浅い」は変更前の基準トレースで、同じ列にある上側の紙の平均枚数が1以下という参考指標。変更後の取り出し費用を保証しない。全既存紙版で記録した構成の追加穴数は、2枚の補助紙のG/Hの合計について、ケースごとの中央値が7〜8個だった。穴数の大域最適値ではない。

**5,415対を同時に採用できるという意味ではない。** 各対を別々に検査した結果で、紙予算と、補助紙を共有したときの穴の和集合の整合性は別問題である。

また、基準の紙を変更せずに使い回せるかも全列挙した。主紙186枚×汎用720順序×挿入7位置を調べたところ、8設計×256商品すべてで利用できる主紙はちょうど1枚だった。今回の8設計では、主紙の選択を増やすには紙の印刷自体を変える必要があった。

## 4. 提出用のC++実装

紙の枚数を維持するため、旧対(a,b)と単独u,vの3枚を、対(u,v)と単独a,bの3枚に組み替える。

```text
共有紙(a,b) + 単独紙u + 単独紙v
    → 共有紙(u,v) + 単独紙a + 単独紙b
```

新しい対は汎用紙だけでは表示できないため、注文処理にも専用の経路を実装した。前の紙と補助紙を回収し、汎用順序を整え、指定補助紙を汎用層へ挿し、主紙を持ち上げ、Hを修正する。実際に印刷する紙のマスクから終状態を作り直し、可視な紙だけを動かす模擬と表示一致を確認して採用する。

| 解法ディレクトリ | 変更の目的 |
|---|---|
| `astrasearch-relaxed` | Hだけを穴化する最初の実装。最大1交換 |
| `astrasearch-perforated` | Gも穴化し、元の担当商品をDAGで再検証。最大1交換 |
| `astrasearch-perforated-union` | 加工後の全終状態への距離を逆BFSで測る。初期設計のハッシュを追加 |
| `astrasearch-perforated-shared` | 最大4交換と補助紙の再利用。元の商品と以前の救済対象をすべて再検証 |
| `astrasearch-joint` | 完成した設計のG/H交換と、壊れた対の修復・再最適化 |
| `astrasearch-joint-hot` | G/H交換を早め、長い再最適化と悪化受理を試す |

いずれも `main.cpp` 単独でコンパイルできる。`CLOCK_SCALE` の既定値は1.0、手元の比較は1.1。強制採用モード `RELAX_FORCE=1` は時間打ち切りを外す研究用であり、通常版の時間制限付き性能と分けて扱う。

`perforated-union` は、まず各補助紙について64集合の中から加工マスクを1つ選び、その後、各方向の上位24候補に対し汎用720順序の全有効終状態を列挙する。合法な汎用紙移動の逆グラフから多点BFSを行うので、選んだ加工マスクに対する平均距離は正確。ただし、すべての加工マスクを最適化したわけではなく、注文中の順序分布も一様とは限らない。

`perforated-shared` では、採用済みの新対と補助紙の担当・列を固定し、同じ補助紙への穴加工を累積できる。各交換を設計のコピーへ適用して全商品の条件を実際の紙で再検査し、失敗なら戻す。追加穴の負担は現在の加工済み紙からの増分だけを数え、以前の救済対象の費用も採用後に再計算する。通常モードは探索途中で累積費用が最良の設計、強制モードは成立した全交換を出す。

共有版の候補順位には近似が残る。以前の救済対象に生じる費用変化は、候補を選んだ後の全体再計算には入るが、各候補を順位付けする段階には入らない。1.35秒も探索の打ち切り目安で、処理中の候補や必須補助紙の初期化まで含む厳密上限ではない。

## 6. 別の構造案も検証した

### 3枚で4商品を持つ局所符号

3枚の6順列から4順列を選んで4商品を表す案は、1窓について表せる4bitパターンが16種類中最大10種類だった。15通りの順列集合を全列挙して確認した。固定したランダム4商品の独立な窓では、平均24窓を別の汎用層に任せる計算になる。ただし、商品群を選び直す最適化や、汎用紙を途中へ挿す方式の不可能性を示すものではない。

### 通常比較器以外の汎用層

4枚不透明の窓を混ぜる構成、白黒のペアを優先順位で使う6枚・8枚構成を、同じ8入力・各2000反復で調べた。通常6枚比較器は8件すべてで必要な70対を作れた一方、混合型は1/8、6枚優先順位型は0/8、8枚優先順位型は必要な72対を2/8で確保した。合法な紙移動の距離まで測ったが、現段階では提出解法に育てる優先度は低い。これは探索方法込みの実験結果であって、構造全体の不可能性の証明ではない。

### 1枚を3商品で共有

固定した基準設計16件で、3商品が差分の和集合を同じ紙の穴として共有できるかを列挙した。各ペアだけなら整合する三角形はあるが、3方向すべての汎用層制約を満たす3商品組は0だった。固定設計の結果であり、3商品共有を目的に汎用層から設計し直す場合の上限ではない。

詳細は `astranova-kernel/RESEARCH.md` と `astra-triples/`。別構造の検討を既存解法の得点比較と混ぜず、核の実験として残した。

### 固定された補助紙1枚では非整合対を救えない

補助紙の取り出しと回収をなくす案として、汎用6枚と補助紙1枚を一緒に常駐させる7枚の制御器も検討した。しかし、**同じ固定模様の補助紙1枚を両商品に使う場合、6枚比較器で非整合だった対は救済できない**。補助紙に任意の穴があっても成立する。

共有主紙の差分窓上で、商品uの比較辺グラフをDとすると、相方vは全辺を反転したグラフになる。次の議論で示せる。

1. 補助紙より上にある汎用紙の集合Sは、比較辺の前件を含む必要がある。`a → b` でbだけが補助紙より上なら、bの誤色が補助紙より先に見えてしまう。
2. したがって強連結成分は、全体がSに入るか、全体が入らないかのどちらか。閉路を持つ強連結成分を丸ごと上に置くと、汎用紙だけで閉路の順序制約を満たすことになり不可能。よって、その成分は補助紙より下にある。
3. 全辺反転でも強連結成分は同じなので、u/vの両方でその成分は補助紙より下にある。
4. 成分内部の差分窓を補助紙が覆うなら、同じ固定色が互いに補色のu/vを両方表示する矛盾になる。内部窓をすべて穴にすれば、汎用紙の元の閉路が残る。

これは表示可能性の証明であり、移動制約を緩めても回避できない。**今回、対の両方向へ異なる補助紙を使ったことには、実装上の都合だけでなく構造的な理由がある。** 1枚常駐案に残る可能性は、すでに可行な対の終状態を増やして移動距離を短くすることに限られる。専用ハンドルの消費、収納列の減少、旧主紙・修正紙の回収まで含めた全体の得点は未測定。厳密な小規模プローブと証明は `astranova-resident/RESEARCH.md` にまとめた。

固定2設計・4種類の常駐模様について、7!順序の表示を直接計算した27,412組の「近接対×模様」でも、両方向が可行な対の増減は0だった。同じ商品対・同じ汎用720順序から常駐紙を最下位に置いて開始した場合の厳密な核距離短縮は0.00679〜0.02632手/対の片方向要求に留まった。この値には常駐紙を最下位へ戻す費用を含めない。予約ハンドル同色の制約後の貪欲選択も最多68対・67対で、必要な70/71対に届かなかった。ただし最大マッチングを解いた結果ではない。今回の1枚常駐案を優先して育てる根拠も得られなかった。

## 7. 次に育てる価値の判断

重要なのは、穴加工を「新しい対1つのための支出」としてだけ評価しないこと。追加穴の負担は、主としてその補助紙の元の1〜2商品が払う。同じ加工済み紙が複数の有用な対を救えば、その負担を各対に重複計上する必要はない。

一方、穴を増やすと、以前救済できた商品の表示を壊す場合がある。今回の共有版は、元の全担当商品と、すでにその紙を補助に使う全商品を再検証し、以前の商品の最短距離が伸びた分も計上した。それでも64件で悪化したので、この実装を交換数だけ増やして育てることは勧めない。

設計の狙いは、次の3項の和を最小化することになる。

1. 商品の組み方・所属列・主紙の取り出しとH修正の費用。
2. 補助紙への穴加工により、元の担当商品で増える費用。
3. 加工済み補助紙を使う各商品の、補助紙の取り出し・挿入・回収と汎用順序変更の費用。

表示できる対を増やせたことは実証済み。しかし、最適化済みの設計へ後から少数の対を追加する今回の方式では、その自由度を利益に変えられなかった。今後進めるなら、加工済み紙を初期の対選択・列割り当てから共同設計するか、補助紙を取り出し・挿入・回収する費用自体を減らす構成が必要になる。4交換の負の結果で全設計空間の可能性を否定することも、5,415対の存在だけで大幅改善を予言することもできない。

非整合対を増やす目的で常駐補助紙を使うなら、上の証明から異なる補助模様が少なくとも2つ必要になる。2枚の専用ハンドルと紙予算、可視性、回収を含む設計へ変える必要があり、これを得点改善が見込めると断定する根拠はまだない。現時点の推奨は、本PRの提出用コードへの置換ではなく、操作費用を消せる構成を小さい厳密モデルで先に選別することである。

## 8. 再現方法と測定上の制限

### 入力・テスター

- 入力は独自生成の `astra-generated-v1`。Python `random.Random(0x4153545241303734 + case_id)` で、64窓中32個黒の相異なる256商品と、直前と異なる商品から一様な1024注文を生成した。
- 公式のChaCha20生成器とは乱数列が異なる。ここでのcase番号は公式seed番号と同じ入力を指さない。入力2000件のSHA256を `generated_manifest.csv` に保存した。
- Rust/Cargoがないため、公式 `tools/src/lib.rs` と `tools/src/bin/tester.rs` の対話・可視性・移動・得点をPOSIX C++23へ移植した。**公式Rustテスター自体で実行した結果ではない。** 次の注文は前の注文の出力を受け取った後にしか送らない。
- 11個のプロトコルテストを通し、得点は既存のPython再生でも独立照合した。表示誤りE、不正操作、2秒超をスコアとは別に記録する。
- このクラウド環境はGCC 13.3で、ユーザーの手元やAtCoderの実行環境と異なる。絶対手数や実時間を、そのままユーザーの10.61手/注文や本番の2秒と同一視しない。
