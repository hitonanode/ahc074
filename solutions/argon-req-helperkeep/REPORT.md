# R4: 旧フィラーを保持したヘルパー計画

## 指摘と実装

助言01-4は「既存の無害なフィラーを残した状態からもヘルパー挿入を試す」と提案する。現行の `Request plans: helpers inside the generic layer` の `try_helpers` は前製品と全フィラーを返却し、cap直下に6汎用紙が連続する状態だけから計画する。指摘は成立する。ただし `finish_handles` は既にヘルパーが覆うハンドルを除いて区間DP・掘り出しを行うため、ヘルパーのハンドル効果を全く考慮していないわけではない。

`helperkeep` は従来計画を残し、`refill_or_return` で旧フィラーを保持・再配置した状態からもヘルパーを試す。固定の挿入深さオフセットを守るため保持紙は汎用層より下へ置き、連続性を検査する。保持紙のハンドル被覆を候補順位と最後の穴埋めから除き、保持紙自身を列から掘り出すヘルパーには使わない。目的関数・既存予算は不変。

## 原因に対応した1回の改修

初期値による候補落ちを避けるため、`helperkeep-screen` は追加の保持計画だけを削除のみの安いpost_optimizeで整えてから順位へ入れる。計画数・後処理候補数は増やさない。

`20261106-072838_*`、24×2→200×2は **−0.002111±0.002632%**、104/1/95。req **0.457019→0.483086秒**。ジャッジ平均1.610664→1.646562、p99 1.775897→1.838730、最大1.847001→1.889273、2秒超え0→0。全件WA / self_wrong / op_label_errors = 0、外部負荷平均0.19・最大0.47コア。初期候補の安い選別だけでは改善しなかった。

測定後、F3_PROFILE有効時だけ追加処理の段番号を3に指定した。既定評価ではマクロが消えるため、評価対象の処理・出力は変わらない。

## 判断

指摘は有効だが、保持計画の追加と原因に対応した改修は、どちらも0.03%の採用基準に遠く及ばない。全仕上げには小さくない潜在利得があるものの、その処理費用は既存予算より不利。2026-11-06 07:00の新方針に従い、ここでR4を不採用として終了する。追加の通常2000件比較は行わない。

対象は汎用層の連続性を保つ旧フィラー保持であり、汎用層内へ複数の旧紙を残した一般化や、ヘルパーと全フィラーを一体に最適化する大きなDPは実装していない。今回の観測と費用から0.03%を時間内で得る明確な見通しはなく、新方針の実験数制限に従ってR5へ移る。

最終screen版はg++/clang++、C++23 -O2 -Wall -Wextra、LOCAL_BENCH有無の4構成で警告なし。検証記録は `../argon-req-helperkeep-screen/builds.log`。
